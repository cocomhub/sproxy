## 目录保密演进：data/meta 目录 → 随机容器 → 父引用解耦

**为什么**：最初设想在底层卷上分 `data/` / `meta/` 顶层目录——但这两个词本身就是结构性标识，等于向
底层存储宣布「这是加密卷」，且目录名直接编码了内容类别，匿名性从根上破功。于是改为**随机命名容器
目录**（5-30 位 `[a-z0-9]`，生成时规避 `meta`/`data`/`secret` 等词）：目录名与内容无关联，底层只看到
一堆互不可分的随机目录与随机文件。

**关键权衡**：随机容器解决了「目录名保密」，但若 meta 里存完整逻辑路径，目录移动就要改写子树内所有
文件的 meta——移动成本 O(子树) 且易被底层观察到批量变更。改用**父引用解耦**：目录 meta 只存
`{name, parent_dir_id}`，文件名只存 basename；目录移动/改名 = 只重写被移动目录自己的 `name`/`parent`
引用（一个文件），**子树零改动**。付出代价是挂载期需沿 parent 链重算逻辑路径（成环须 fail-closed 防
栈溢出），换取的是「移动零改内容」这一干净语义。

**最终态**：底层全透明（随机容器 + 三层命名），目录间完全解耦，逻辑路径沿 parent 链恢复，目录/文件
移动均不触碰子树内容。

## 删除语义：墓碑 + GC → 即时物理删 + GC 可选

**为什么**：最初沿用「墓碑 + 后台 GC」——删文件只打 `deleted` 标记，靠 GC 后续物理清。但后台 GC 是
并发正确性的泥潭：同一套「判定孤儿再清理」的 GC 路径**三次**引入数据丢失竞态（误删存活分块 / 挂载期
瞬时读故障误判存活文件 / epoch 窗口内已提交的写在快照后清理）。GC 复杂度失控本身就成了最大风险。

**权衡**：加密卷的**默认形态不应该依赖「能删错数据的后台 GC」保持正确**。转向即时删除：Delete 一次 /
持锁删完 meta + 全部分块，删即释放、重启不复现、正确性不依赖后台 GC（先删 meta 再删分块——meta 删
失败则分块全在，可重建完整文件，不产生幽灵）。GC 降级为**可选维护工具**：默认不启动（`gc_interval` 零
为 0），仅供远程卷 / 多进程共享场景显式启用作孤儿兜底。

**最终态**：默认路径是自包含的「删即释放」，零后台依赖；后台 GC 只在多进程共享卷场景作为预案保留。

## KDF 档位化：从常量到用户可调，再从真实档到轻量 mock

**为什么**：KDF 最初是固定常量 scrypt 参数。随即意识到两点——（1）不同部署的吞吐 / 内存预算差异巨大，
常量档无法兼顾；（2）阿里云类服务器就地实测看到的 memory 峰值随并发线性放大，固定 high 档会让大卷
挂载内存爆炸。于是把 scrypt 参数**随 Algorithm 版本化**：每档 = 不同 AlgoVersion + 派生域，跨档
fail-closed，调整强度就是登记新版本、不破坏既有 blob。

**另一权衡**：为根除「高熵密钥上的非必要重派生内存」，派生强度并不决定安全（secret 是 256-bit 高熵，
暴力破解本就不可枚举，KDF 只做域分离），所以默认档取性价比档 `standard`（2^14），`high` 只供低熵
兼容，`low` 供测试/低配。

**测试到底**：测试套件跑真实 scrypt 会让组装层测试白白付出百毫秒级派生（大卷数百文件即分钟级）。
于是「测试用轻量 mock」从「极低档真实 scrypt」演进出独立子包 `mockkdf`：HKDF-SHA256 轻量派生
（~µs）+ **仍走真实 AES-GCM**——组装正确性（密钥/盐/格式传递、密文往返）仍真实验证，仅派生轻量化；
真实 high 档的内存实测收敛为一次性基准。**生产禁配 mock**，算法可靠性始终由真实档维护。

**loadGate 自适应（配套）**：派生并发上限不靠人工定，而按**注册档位的真实内存**（RFC 7914
128×r×N）反推预算（512MiB），档位越高并发越收窄。内存测算是类型级纯算术、与 KDF 覆盖正交，故 mock
档下发并发不受 mock 派生拖慢。

**最终态**：三档 `high / standard / low`（可配）+ `mockkdf` 测试子包；派生并发上界由内存预算自适应。

## 字节单位：裸 int64 → 人类可读 ByteSize

**为什么**：config 里裸 int64 字节字段（如 `meta_pad_bytes`、`max_file_bytes`）不可读、易错位（把
「1GiB」填成 `1073741824`）。为此引入 `pkg/units/sizex.ByteSize`（int64 底层命名类型）：接受纯数字 /
SI（`5GB`）/ IEC（`5GiB`）人类可读格式，YAML 与 viper 双解码（TextUnmarshaler），独立于
`pkg/server` 子包 / cmd（go.work 多 module 均可引用）。internal/size 既有逻辑保留不动，后续单独统一
迁到本包。

**最终态**：config 字节字段统一 `sizex.ByteSize`，渲染成可读字符串、内部按 int64 计算。

## 过度设计收敛：Dedup 降预留、Erasure 标实验

**Dedup**：曾设想整文件内容去重（卷级池 + 引用计数）。命名要求内容哈希截断锚定（64-bit 键），在跨
实例大规模下碰撞风险不可忽略；且复杂度 / 正确性成本集中在共享元数据。方案 A 收敛：**去重降级为预留
能力**——装配层不接线（不解析 `extra.dedup`）、生产不可达，实现路径保留为实验代码供未来独立内容寻址
子系统承接。理由是「默认形态不该被高风险高复杂度的可选项拖累」。

**Erasure**：纠缠纠错也实现后「生产验证」不充分——XOR parity（k-of-k+1）数学正确但未在大卷 / 多进程
下证；但各有价值故不删。收敛为**显式标注 experimental**：默认关闭、退出默认正确性承诺；为单块损坏 /
丢失恢复的额外可选能力（后续 Reed-Solomon 多块纠错为演进方向）。

**共同收敛原则**：已实现但未生产验证的能力一律**标注实验性 + 默认关**，不进入「默认正确性」承诺；
可留用未来承接的更完整能力（内容寻址、RS 纠删码）则**标预留**。

**最终态**：默认配置形态简单、正确性自足（无后台依赖、无未验证能力参与）；Dedup 预留、Erasure 标实验。

## 对抗性审查驱动的收敛（怎么做对的）

**为什么能收敛**：全套方案（分块格式、目录解耦、删除、KDF 档位、GC）经历多轮对抗性审查，每轮聚焦
「错误场景会怎样」——逐个检查数据丢失 / 竞态 / 冲突 / 跨重启一致性 / 匿名性泄漏面 / 内存峰值上的弱
点。收敛机制是：凡是**审查暴露的「一条会丢数据/能隐私的路径」必须即刻修**，而不是「记 TODO」；对于
反复出现多次修正的后台 GC、去重等**反复证明不稳定的语义，直接降级 / 移除**，是最终防线不是补丁。

**结论**：收敛结果是「默认讨巧、显式弱化」——默认动线（写 / 读 / 删 / 移动）在单进程、无后台依赖下
是简单且 fail-closed 的，需要扩展的（多进程 / 远程卷 / 纠错 / 去重）每一样都显式配置、明示实验性、
退出「默认正确性」承诺，且全程未引入 **Critical** 级数据安全缺陷。

**最终态**：公开的「最佳实践」路径 = 默认档位 + 默认删除语义 + 可选实验能力显式开启，行为可控、可解释。
