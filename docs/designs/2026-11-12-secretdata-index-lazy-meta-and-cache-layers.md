# secretdata 索引快照：热/冷分层与元数据缓存组合策略

> 状态：**设计（待评审）** ｜ 日期：2026-11-12 ｜ 相关：#1113（快照内存优化）、#1116（gzip 直连解码）、#1110（R46 S2 checksum）
>
> 替换性说明：本方案**取代**此前讨论过的「按目录聚合清单缓存」与「WAL + 定期压缩」两条路线（见 §7 取舍）。

## 1. 问题定论（实证，非推断）

### 1.1 症状
加密卷（secretdata）启动期内存峰值可达 **GB 级**，在 WSL 内被 OOM killer 杀死（`Out of memory: Killed process (sproxy)`）。

### 1.2 实测数据（真实生产 meta，工具见 §8）
样本 = 一个真实文件 meta（`SDMC1` 本地缓存，解密后为 JSON）：

| 项 | 实测值 |
| --- | --- |
| meta JSON | **87.0 MB** |
| **反序列化后 Go 存活内存（HeapAlloc）** | **78 MB**（87 → 166 MB）|
| chunks / blocklets | 23 / **430,652** |
| 每条 blocklet 内存 | **约 191 字节** |
| ⇒ 单个大文件常驻内存 | **78 MB** |

本地 metacache 目录实测：**9,489 个文件 / 5.29 GB**，**最大单文件 86.98 MB**（中位数仅 1,217 B）。
⇒ 只要**少数大文件**的 meta 进入内存 ⇒ **几 GB 常驻 ⇒ OOM**。

### 1.3 三轮假设推翻记录（供后人不再重走）
| 轮次 | 假设 | 实测结论 |
| --- | --- | --- |
| 1 | 主体是 `Dirs`/`DirSegs`/`DirIDs` | ✗ 30 万目录合成夹具 gzip 仅 **7.3 MB** |
| 2 | `ChunkInfo.FileName` 重复是主因 | ✗ 占 **0.001%** |
| 3 | **主体是 `Chunks[].Blocklets`，且本不该常驻** | ✓ **定论** |

## 2. 根因：冷热耦合，且已有设计被绕过

### 2.1 内存索引把冷结构焊进热记录
`metaEntry.meta *shardseal.Meta` 使**每个文件**常驻完整 Meta（含 `Chunks[].Blocklets`、`Parity`、`Windows`）。

### 2.2 热路径根本不用它（实证）
| 路径 | 是否访问 `meta` | 证据 |
| --- | --- | --- |
| **`ListDir`**（最热）| **不访问** | 只读 `s.index`/`s.dirs`/`s.dirMTime` + 条目 size/mtime |
| **`Stat`** | **只读 1 个字段** | `e.meta.Original.SHA256`；注释明确「meta 可能为 nil ⇒ nil 时 checksum 留空（调用方 stat 兜底）」|
| `openRead` / `OpenRangeRead` | 需要（冷）| `ensureEntryMeta` 的**全部 2 个调用点** |

### 2.3 按需加载机制**早已存在**，被快照绕过
```go
func (s *SecretdataFS) ensureEntryMeta(ctx, e *metaEntry) error   // meta_cache.go:221
func (s *SecretdataFS) readFileMetaFast(...)                      // :173 先查 compact metacache → 未命中读 meta blob
```
⇒ 设计意图本是「**meta 可为 nil，用时再读**」。**快照把 `Meta` 全量填满，把这个设计废掉了。**

⇒ **结论**：不是「缺设计」，而是「**已有设计被绕过**」。修复方向是**让快照回到设计意图**，而不是新造架构。

## 3. 新方案：四层数据管理

```
L0  热索引（本地快照，必常驻）              ← 零远端调用
    rel → {size, mtime, origSHA256, dirSeg, metaName, dataDir, baseVersion, phys}
    覆盖：list / stat / search / 目录浏览
    体积：~150 B/文件 ⇒ 850 文件 ≈ 130 KB（对比现状快照 241.8 MB）

L1a 元数据磁盘缓存（metacache，持久 + 配额 + LRU）   ← 命中则零远端
    rel → 解密后的 Meta（Chunks/Blocklets/Parity/...）
    跨重启有效；容量可配置（默认建议与卷规模挂钩）

L1b 元数据内存缓存（LRU，字节计量）               ← 命中则零远端 + 零反序列化
    仅缓存"最近真正被读取"的文件 meta；有硬上限，绝不随卷增长

L2  远端 meta blob（权威）                     ← 仅 L1a/L1b 未命中时读
    调用面 = 「被真正读取的文件数」，而**非**「全卷文件数」
```

**核心改动只有一条**：快照**不再序列化 `Meta`**；加载后 `e.meta = nil`，交给既有 `ensureEntryMeta`。
同时把 `origSHA256`（← `meta.Original.SHA256`，即 **#1110 R46 S2 的动机**）提升为 **L0 扁平字段**，
使 `Stat` 不需要 meta。

## 4. 命中率保证：组合处理策略（本方案重点）

> 目标（用户明示 2026-11-12）：**热文件 meta 本地有缓存；批量操作也应大概率命中缓存；只有不存在的才走远端。**

### 4.1 按「所需字段级别」路由（收益最大的一条）
批量操作先声明它需要什么，**能在 L0 满足的绝不碰 meta**：

| 操作类型 | 所需字段 | 走的层 | 远端调用 |
| --- | --- | --- | --- |
| 列目录 / stat / 搜索 | L0 热字段 | L0 | **0** |
| checksum 巡检（按 size/checksum 比对）| L0 `origSHA256` | L0 | **0** |
| 下载 / 纠删恢复 / 深度校验 | blocklets | L1b → L1a → L2 | 仅 miss |

⇒ 很多「看起来需要全量 meta」的运维操作，实际只需热字段 ⇒ **直接消灭远端调用**。

### 4.2 批量操作的两阶段（miss 集才走远端）
1. **全量查 L1b → L1a**（本地，快，可并发无上限）
2. 得到 **miss 集**，只对 miss 集发起 L2 请求

⇒ 重复执行同类批量操作：**第二次全命中**（因为 4.3 回填）。

### 4.3 回填 + 去重 + 限速
- **回填**：L2 取回后立即写 L1a（磁盘）并插入 L1b ⇒ 后续同文件全命中
- **去重（single-flight）**：同一 rel 的并发请求合并为一次远端调用
- **限速/并发上限**：远端调用走统一闸门（复用既有可靠性设施，见 §6），避免打爆远端 CLI
- **失败退避**：可重试错误走既有重试/事项机制，不新增一套

### 4.4 预热（可选，默认关闭）
后台、限速地把「常用/近期活跃」文件的 meta **拉到 L1a（磁盘，不常驻内存）** ⇒ 让首次批量操作也大概率命中。
- 只预热到 L1a（磁盘）⇒ **不增加常驻内存**
- 必须有速率上限与可取消（`disable_*` 语义，见 §5 配置纪律）

### 4.5 缓存淘汰与保护
- L1b：**按字节的 LRU**，硬上限（如 256/512 MiB），**绝不随卷规模增长**
- L1a：磁盘配额 + LRU；淘汰**不得**影响正确性（永远是缓存，可重建）
- **正确性红线**：L1a/L1b **永不作为唯一真相**；未命中/校验失败 ⇒ 回落 L2

## 5. 配置与既有纪律

| 配置 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `meta_cache.dir_quota` | ByteSize | 非零默认 | L1a 磁盘配额上限（`sizex.ByteSize`，遵守硬规则 19）|
| `meta_cache.mem_quota` | ByteSize | 非零默认 | L1b 内存 LRU 上限 |
| `meta_cache.disable_prewarm` | bool | **false** | 语义反转（默认预热开启），遵守硬规则 7c |
| `meta_cache.prewarm_rate` | 速率类 | 保守默认 | 预热速率上限 |

## 6. 与既有能力的关系（不重复造轮子）

| 需要的能力 | 复用对象 |
| --- | --- |
| 解密 meta 的磁盘缓存 | **既有 `metacache`（`SDMC1`）** —— 本方案只是给它加**配额与 LRU** |
| 可变尺寸文件对映射 | 既有 `compactKey`/`metaCachePath` |
| 并发闸 / 排队 | `pkg/waitq`、`pkg/quota`（禁止新写 `sync.Cond`）|
| 失败重试闭环 | `pkg/server/issues`（有界重试 → 转人工）|
| 远端并发上限 | 既有 `pkg/volume/ext/baidupcs` 的 gate/cooldown 设施 |
| 目录级 checksum 索引 | 既有 `pkg/volumestate`（R46）；**本方案不新增目录聚合缓存** |
| 惰性加载入口 | **既有 `ensureEntryMeta` / `readFileMetaFast`**（不新造）|

## 7. 与另两条路线的取舍（为什么不选）

| 路线 | 为什么不做（现在） |
| --- | --- |
| **按目录聚合清单缓存** | ① 引入聚合一致性（需目录级锁 + 重试闭环）；② 热字段提升到 L0 后**已无必要**；③ L0 是扁平索引，比聚合**更简单** |
| **WAL + 定期压缩** | 它解决的是**写路径写放大**，而本问题瓶颈是**读路径内存**；且引入重放窗口/压实时机/崩溃恢复三类复杂度，还要与 `pkg/recovery`、`pkg/audit` 划界（违反「同一语义只留一份实现」）|
| **`ls -l` 取 checksum 做新鲜度** | 只影响「L0 的 checksum 是否新鲜」，**不是本方案成立的前提**；可后续单独评估（本仓曾实测退化）|

## 8. 分期实施

| 阶段 | 内容 | 风险 |
| --- | --- | --- |
| **P1（核心，本 PR）** | 快照去 `Meta`；`origSHA256` 提升为 L0；加载后 `e.meta = nil`；`deleted` 按需（仅冷路径用）| 低 |
| **P2** | L1b 内存 LRU（字节计量 + 硬上限）；`ensureEntryMeta` 走 L1b | 低 |
| **P3** | L1a 磁盘配额 + LRU；miss 集批量加载 + single-flight + 限速 | 中 |
| **P4（可选）** | 预热（限速、默认开启、可 `disable_`）| 中 |
| **P5（可选）** | 批量操作按「字段级别」路由（§4.1）| 低 |

P1 单独就已拿走 **~99.9%** 的收益（快照 241.8 MB → 约 0.1–1 MB；内存 790 MB → 极小）。

## 9. 验证方法

### 9.1 单测（TDD，先红后绿）
- **快照不含 Meta**：序列化后断言无 `meta`/`blocklets` 键；加载后 `e.meta == nil`
- **热路径不加载 meta**：`ListDir`/`Stat`/`Search` 后断言**零次** meta 加载（用可注入计数器）
- **冷路径触发且命中缓存**：`OpenRangeRead` 后断言加载 1 次；第二次**命中 L1b ⇒ 0 次**
- **miss 才走远端**：L1a 命中 ⇒ 远端调用 0；未命中 ⇒ 恰 1 次
- **上限生效**：L1b 超限触发淘汰且不超配额
- **变异验证**：删除「不加载」的短路 ⇒ 热路径计数测试**必须红**

### 9.2 真机
- 重启测：快照体积、启动峰值内存、启动耗时（对比 P1 前后）
- 批量操作（如全仓巡检）测：**远端调用次数**与**第二次执行的命中率**

## 10. 风险与回退

| 风险 | 处置 |
| --- | --- |
| 快照去 Meta 后，某些调用方隐式依赖 `e.meta != nil` | 编译期+测试期扫描；`ensureEntryMeta` 兜底；`Stat` 的 checksum 回落 L0 `origSHA256` |
| 批量操作远端调用暴增 | §4.1 字段级别路由 + §4.2 miss 集 + §4.3 限速/去重；必要时提高预热 |
| 缓存与远端不一致 | L1a 记录来源指纹；校验失败即丢弃并回落 L2（永不作为真相）|
| 回退 | 每个阶段独立可回退；`meta_cache.*` 支持关闭；快照带版本号，不适用即回退全量扫描（既有 fail-safe）|

## 12. 与相关设计的关系（避免重复劳动）

本仓有两份**方向互补、易被混淆**的设计，特此划清边界：

| 文档 | 解决的问题 | 手段 | 状态 |
| --- | --- | --- | --- |
| **本文**（`2026-11-12-...lazy-meta-and-cache-layers.md`） | **启动内存 / 读取成本**（OOM 根因） | 快照**热/冷分层**（L0 快照 / L1a 磁盘 / L1b 内存 / L2 远端）+ 命中率组合策略 | P1–P3、P5 **已交付** |
| `2026-11-11-checksum-ledger-read-path.md` §10 | **本地 checksum 台账退场** | 方案 D：**目录级 checksum 索引**（`dirindex`，写路径同事务更新；D1–D4） | 建议先做 D1 |

**交集与边界**：
- 两者都涉及「目录级元数据」，但**对象不同**：本文管的是**单个文件的冷结构 `Meta`**（含 blocklets）
  如何不进热内存；`dirindex` 管的是**目录下的 checksum 聚合/索引**（用于让台账退场）；
- **命名**：该文已明确 `secretdata` 的 `KindDirMeta` 是**逻辑树**（改名/移动权威记录），
  新方案须**另起名 `dirindex`** ⇒ 与本设计的 `L1b`（元数据内存缓存）**无命名冲突**；
- **顺序**：本文已交付的分层**不依赖** `dirindex`；`dirindex` 亦可独立推进（目标不同）。

⇒ 若后续要做 `dirindex`，请**先读该文 §10**；若要动「meta 何时加载/淘汰」，请以本文 §3–§5 为准。
