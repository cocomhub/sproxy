# checksum 单源化：方案深析与处理建议（2026-11-12）

> 承接 `docs/archive/2026-11-11-checksum-ledger-read-path.md`（口径裁定 / S1–S2 已交付事实 / S3 阻塞点 /
> 「候选方案 D：meta 单源 + 目录 meta」草案）。原件已于 2026-11-14 归档并精简（**分期清单与实现细节已移除**），
> 本文件承载**完整深析与分期建议**，是当前该议题的决策支撑文档。
> 本文对候选方案做**逐维度深析（性能/可靠性/稳定性/正确性/一致性）**，并给出带量化依据的处理建议与分期。
> 实测数据来自本机微基准（Windows/SSD，含 FS 缓存）——**只代表量级与相对关系**，非 CI/生产绝对值；复现脚本见文末附录。

## 1. 问题定义与非目标

**问题**：`list`/`search`/`stat` 的 checksum 目前来源分散（条目自报 → sidecar → 台账），
台账承担**聚合/索引**角色；但台账是 per-owner 单 JSON（整体重写），且 `search`、远端卷列表仍依赖它
⇒ 无法停写（S3 阻塞）。

**目标**：让**本地/可信任卷**的 checksum 读路径收敛到「对象 meta 单源」，台账退为导入源（最终可删）。
**非目标**：远端卷（webdav/sftp/ftp/pikpak，无 sidecar 写侧）列表 checksum 的语义变更（需单独裁定）。

## 3. 实测数据（量级与相对关系）

### 3.1 读侧（N=2000，单 sidecar ≈285 B，目录索引 238 KB）

| 动作 | 耗时 | 备注 |
| --- | --- | --- |
| (a) 顺序读 N 个 sidecar | **54.4 ms** (27.2 µs/文件) | 现状 S2 的 cache-miss 路径 |
| (b) 单读目录索引 + JSON 解析 | **1.66 ms** | 用户提议的核心收益 |
| (c) `ReadDir` | 0.52 ms | 列举本身 |
| (d) **8 并发**读 N 个 sidecar | **11.7 ms** (5.9 µs/文件) | 不改任何状态即可获得 |
| 目录索引全成本 (c+b) | **2.18 ms** | ⇒ 相对 (a) **≈25×**；(d) 相对 (a) **4.6×** |

### 3.2 写侧（每文件更新一次索引）

| 动作（N 次） | N=300 | N=1000 | 累计写入 (N=1000) |
| --- | --- | --- | --- |
| (f) 朴素 read-modify-write 整索引 + rename | 168 ms | **582 ms** | **58 MB**（≈500× 追加日志） |
| (g) 追加日志 `O_APPEND` | 1.58 ms | **4.9 ms** | 116 KB |
| (h) 固定小文件写（线性下界） | 36.7 ms | 123 ms | 116 KB |

**结论（关键）**：
1. **读**：dirindex 有 ≈25× 量级收益；但**只把 S2 的顺序读改成 8 并发**就有 4.6×，且**零新状态、零一致性风险**。
2. **写**：朴素「每文件重写整索引」是 **O(N²)**（大目录直接不可用）⇒ 若做 dirindex，**必须**是
   **追加日志 + 压实**（每文件 ≈5 µs，与今天写 sidecar 同量级）。

### 4.1 逐维度深析（针对 B，即用户提议的可行形态）

**性能**
- 读：cache-miss 大目录由 54 ms → **2.2 ms**（≈25×）；命中仍为 0（`volumestate` 快照）。
  搜索若也走索引，则 `search_index.go:724` 的台账读可整体消失。
- 写：追加日志 **≈5 µs/文件**（与写 sidecar 同量级）；**压实**在后台按阈值触发（日志 ≥ 1 MB 或 ≥ 2×条目数），
  成本摊销到 N 次写之后；压实期间持目录锁（见下）。
- 空间：索引 ≈119 B/条目（实测），与 sidecar 相当；压实后单文件；可加**分片**（每 1k 条目一片）规避超长目录。
- 内存：索引数据**不**进 `volumestate` 快照的常规路径（否则与并行工作中的 snapshot-memory 优化冲突）——
  按目录惰性加载 + 受条目预算约束。

**可靠性**
- 索引是**可派生缓存**：丢失/损坏/过期 ⇒ 回退 S2（sidecar）⇒ 回退台账；**永不因索引失败让用户操作失败**。
- 写入失败（磁盘满/权限）⇒ **必须上报**（`pkg/server/issues` 新 Kind + 定期重试），不得静默（沿用 secretdata
  `CleanupStaleDirMeta` 的「重试直到成功 + 达上限转人工」闭环）。
- 崩溃一致性：日志追加**无 fsync**（或批量 fsync）⇒ 断电丢尾部；读取时**逐行校验**（非法 JSON/校验和不符 ⇒ 跳过）；
  压实用 `tmp + rename` 原子替换，**先 rename 再截断日志**。

**稳定性**
- 需**上界**：单目录日志字节上限、条目上限（超限**强制压实**或转分片）；压实抖动需限速（复用 scheduler + 限流）。
- 目录热点：同一目录高频写 ⇒ 追加日志天然抗写放大（仅 append）；但**压实**会出现长锁窗口 ⇒ 需
  「压实期间 append 到新日志、旧日志只读」的双日志切换（类似 LSM）。
- 可观测：`dirindex_{hit,miss,stale,rebuild,append_fail,compact_total/duration}` 指标 + 告警。
- 可关闭：特性开关默认 **关闭**（`dirindex.enable: false`，符合 AGENTS 7c 的「默认 false」语义），
  且失败路径与关闭路径**同一条**（回退 S2）⇒ 回滚成本≈0。

**正确性**
- 不变量：**索引条目 ≡ 该文件 sidecar 的 `TotalSHA256`**。
- 校验：读取索引后按条目 `size/mtime` 与目录实际条目比对；不符 ⇒ 视为 stale ⇒ 回退并**增量重建**。
- 边界：空文件（sha256 恒 `e3b0c442…`）仍写索引；sidecar 缺失（历史数据/旁路写）⇒ 索引**不填**（与 S2 同口径，
  由消费方 `stat` 兜底），不伪造。
- 仲裁：目录改名/移动产生多份索引时，沿用 secretdata 的**同一套** `Version→mtime→Name` 判据（**禁止分叉**）。

**一致性**
- 写路径顺序：**写文件 → 写 sidecar → 追加索引日志**。任一后续步骤失败 ⇒ 索引可能 stale ⇒ 读侧校验兜底
  （fail-safe 方向正确：性能降级，不产生错误结果）。
- 目录改名/移动/删除：索引随之 rename/delete（best-effort + 失败上报）；`MakeDir` 建立空索引（或惰性不建）。
- 并发：进程内按目录互斥 + 跨进程 `pkg/server/filelock`（**注意 Windows 为 no-op** ⇒ Windows 单进程假设需写入文档）。
- 与 `secretdata.KindDirMeta` 的关系：**命名与语义分离**（建议 `dirindex`），避免与「逻辑树权威记录」混淆；
  两者都需仲裁机制，但**不得共用文件名/挂点**。

## 5. 处理建议（推荐路线）

> 原则：**先用最便宜的手段吃掉大头的性能收益，再按「可派生缓存」的定位引入 dirindex；全程保持可回退。**

| 阶段 | 内容 | 收益/验收 | 风险 | 回滚 |
| --- | --- | --- | --- | --- |
| **P0（建议立即，1 个小 PR）** | **S2 顺序读 → 有限并发批量读**（8 路，`errgroup`/信号量）+ 指标（miss 次数 / 批量耗时 / sidecar 失败数） | cache-miss 大目录读 **4.6×**（实测 54→12 ms/2k）；零新状态 | 极低（纯读并发，无新文件） | 改回顺序（1 行） |
| **P1（结构性，独立 PR）** | **dirindex 格式 + 写路径（追加日志 + 压实）** + 校验 + 失败上报（新 `issues.Kind`）+ 结构门禁（写覆盖/一致性自检），**读路径不变**（开关默认关） | v1：写侧 ≈5 µs/文件、压实摊销；读侧未启用（零行为回归） | 中（写路径复杂度、Windows 锁语义） | 开关关闭 ⇒ 完全走 S2 |
| **P2** | 读路径：**优先 dirindex → 回退 S2 → 回退台账**；打开开关（灰度）；补 e2e（大批量目录/并发写/崩溃重启） | 读 **≈25×**；台账读路径在本地侧可停用 | 中 | 关开关 |
| **P3** | 迁移/自愈：首列举**重建**索引（逐 sidecar 聚合，一次落盘）+ 压实调度 + 指标/告警 | 存量目录自动收敛 | 低 | 重建幂等 |
| **P4** | **台账只读化**（原 S3/S4）——仅本地侧；`search` 改走索引；远端卷按方案 **D** 单独裁定 | R46 归零、删门禁 | 中（需 P2/P3 稳定） | 保留台账写入（开关） |

**要点**：
1. **P0 先做**：它以 1/10 的成本拿到 4.6×，可能让「大目录 list 慢」问题不再紧迫；也为 P1/P2 提供指标基线。
2. **dirindex 必须 append-log + 压实**（实测朴素 RMW 是 O(N²)，不可接受）。
3. **索引是缓存**：任何异常 ⇒ 回退，绝不让用户操作失败；写入失败必须**上报 + 重试**（复用 issues）。
4. **命名与先例分离**：`dirindex` ≠ secretdata `KindDirMeta`；仲裁规则**复用同一判据**但**代码单一实现**。
5. **门禁**：新增 P1 的门禁（见 §6），否则「漏更新一处索引」会变成静默一致性缺陷（R45 的同类教训）。
6. **远端卷（方案 D）**：建议**单独裁定**为「列表 checksum 留空 + 客户端按需 `stat`」，并把该语义写入 API 文档；
   本路线不覆盖远端。

## 6. 建议新增门禁（P1 必备）

| 门禁 | 断言 | 反例 |
| --- | --- | --- |
| 写覆盖（结构） | `trusted.Wrap` 的**全部**变异方法（`WriteFile`/`WriteIfAbsent`/`WriteFromStagedPath`/`Rename`/`Move`/`Delete`/`DeletePrefix`/`MakeDir`）在成功返回前都触达 `dirindex` 更新（或显式登记"为何不需要"） | 新增一个变异方法而漏更新 ⇒ 必须红（同 R45） |
| 一致性自检 | 读侧对索引条目做 `size/mtime` 校验；构造"索引 stale"夹具 ⇒ 必须回退 S2 且计数 stale（不得返回错值） | 直接信任索引 ⇒ 红 |
| 崩溃/部分写 | 人为截断日志尾部/写入非法行 ⇒ 读取必须跳过并标记重建 | 解析失败即报错 ⇒ 红 |
| 预算/上界 | 单目录日志/条目超阈值 ⇒ 强制压实或转分片（不得无界增长） | 无阈值 ⇒ 红 |
| 回退链 | 索引缺失/损坏/开关关闭 ⇒ 结果与 S2 逐条等价 | 回退后 checksum 缺失 ⇒ 红 |

## 7. 决策点（需用户裁定）

1. **是否按 P0→P4 推进**？建议：**P0 立即做**（便宜、无风险）；**P1 视 P0 后的基线决定是否继续**
   （若 P0 后大目录 miss 已可接受，P1–P4 可降级为「按需立项」）。
2. **远端卷列表 checksum 语义**：接受「留空 + 客户端 `stat` 兜底」？（这决定 S3 阻塞点② 能否解锁）
3. **Windows 语义**：`filelock` 在 Windows 是 no-op ⇒ 若要求跨进程索引一致性，需另行方案（或声明 Windows 单进程假设）。
