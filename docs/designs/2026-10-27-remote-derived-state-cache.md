# 远端派生状态缓存：通用方案与删除失效纪律

> 状态：**设计（待实施）**。来源：2026-10-27 「外部卷删除/改名报缺少 checksum」缺陷的根因复盘
> ——顺着「列表为什么不带 checksum」追下去，暴露的是**整个仓库缺少统一的「远端派生状态」缓存
> 分类与失效纪律**，各卷各写一套（secretdata 有 `invalidatePrefix`、baidupcs 的 dlink 删除时
> **完全不清**、搜索索引/checksum 台账只有本地卷生效）。本文给出一份可执行的通用方案。
>
> 已落地部分（不在本文范围）：前端 `resolveOpChecksum` stat 兜底（PR #860）。

---

## 一、问题陈述

服务端持有一批**从别处（远端卷内容 / 对象内容）派生出来的本地状态**。它们让操作变快，
但**一旦底层事实变化，本地副本就可能撒谎**。仓库现状是逐点解决，没有分类、没有失效总线：

| 现象 | 直接后果 | 归因 |
|---|---|---|
| 外部卷列表不带 checksum | Web UI 删除/改名**功能死路**（已修：stat 兜底） | 缺「派生根」的产出契约 |
| `baidupcs.Storage.Delete` 不清 `dlinkCache` | 删后同名重建可能命中旧直链 → 404/取到旧内容（靠自愈掩盖） | 删除无失效钩子 |
| `secretdata` 内存索引仅在挂载时 `loadIndex` 一次 | 用户用百度 App / 另一实例改动卷 ⇒ **幽灵条目、旧哈希**，永不收敛 | 无跨进程有效性判据 |
| 搜索索引 / checksum 台账只覆盖本地卷 | 外部卷搜不到、无台账（当前由 stat 兜底顶着） | 派生状态按卷类型分叉 |

## 二、分类（这是通用方案的骨架）

按「**陈旧会造成什么后果**」而非「存在哪」来分类，因为失效策略由后果决定。

| 类别 | 定义 | 陈旧后的后果 | 可接受的过期强度 |
|---|---|---|---|
| **A 内容派生值** | checksum / size / mtime / 明文块 | **安全**：错误的「校验一致」会放过被篡改文件；错误的「不一致」会误拒合法操作 | **强一致**（或 fail-closed 不用），绝不允许「乐观复用」 |
| **B 句柄/凭据** | dlink URL、access token | **可用性**：请求失败，但失败**可观测且可自愈**（重新签发） | 弱一致（TTL + 失败自愈）即可 |
| **C 结构视图** | 目录树 / 文件索引 / 聚合列表 | **可见性**：看到已删文件、看不到新文件 | 中（需明确收敛路径，不可永久漂移） |
| **D 聚合账本** | 配额用量、容量计数 | **准入**：假 507（拒绝合法写入）或过度准入（超限） | 强（但允许有界漂移 + 自愈对账） |

**判定口诀**：*能导致「把坏数据当好数据」的是 A 类，必须强一致；只影响「这次失败了下
次再试」的是 B 类，TTL 就够*。

## 三、通用方案：四层机制

### 3.1 第一层——产出契约（谁必须提供什么）

给能力接口加**显式契约**，让调用方不必猜：

```go
// pkg/sync（既有可选能力接口风格）
// Entry 已带 Checksum/Checksums 字段。契约：
//   - ListDir/Stat 返回的 Entry.Checksum **可以**为空（= 未知，调用方按需 stat）；
//   - 若底层能在**列举时零额外成本**给出（内存态/已扫描），**必须**填。
```

落地动作（按成本排序，全部零协议变更）：

| 卷 | 列举补 checksum | 成本 | 说明 |
|---|---|---|---|
| secretdata | **必须填** | O(1) | `meta.Original.SHA256` 已在内存索引里，纯读字段 |
| 本地卷 | 已填（台账/实时算） | O(1) | 现状 |
| baidupcs | **不填**（声明 unknown） | 每文件 1 RTT | 由消费方 stat |
| S3 | ETag 可填（列 already 有） | O(1) | 明确标注 `ChecksumType="etag"` ≠ SHA-256，消费方按算法取交集 |

**关键约束**：`ChecksumType` 必须自述算法，禁止把 ETag 当 SHA-256 比较
（`sync.Equal` 的 `commonChecksumAlgo` 已有该语义，此处只是要求列举侧也如实标注）。

### 3.2 第二层——消费侧兜底（永不依赖缓存齐全）

已在前端落地，服务端同类缺口按同一模式补：

```go
// 任何「需要 checksum 才安全」的写操作：
//   ① 调用方给了 → 用；
//   ② 没给 → Stat/FileMeta 现取（A 类禁止用缓存猜）；
//   ③ 仍拿不到 → **明确拒绝**（fail-closed，不静默跳过校验）。
```

这正是 `resolveOpChecksum` / `FileClient.resolveDeleteChecksum` 的形状。**要求**：新增的 A 类
消费点一律走这个三段式，而不是自己读某个 map。

### 3.3 第三层——失效总线（本文的核心缺口）

现状：每个缓存自己记得在写/删时清自己，**漏一个就是幽灵**（baidupcs dlink 就是这样漏的）。
方案不是再造一个大而全的缓存层，而是**统一「对象身份 + 失效信号」的传达方式**：

```go
// pkg/sync —— 对象身份（已有 LogicalKey 用于写幂等，这里扩为失效键）
type ObjectRef struct {
    Volume string // 卷名（"" = 本地默认卷）
    Path   string // 卷内相对路径（正斜杠）
}
```

规定：**任何 FS 实现，在 `Delete` / `Rename` / `WriteFile` 成功后，必须让自己的派生状态
对该 `ObjectRef`（Rename 还有旧 ref）** 不再生效。三条可接受实现，按代价选：

| 实现 | 适用 | 例子 |
|---|---|---|
| **① 即时清除**（同步按键删） | 键空间有限且可精确映射 | secretdata `invalidatePrefix`、checksum 台账 `Delete(rel)` |
| **② 代际递增**（条目带 generation，写/删时 +1，读时比对） | 结构化视图（索引） | search index 可改为 `(owner,rel,gen)` |
| **③ 只标 TTL 短**（≤ 秒级） | B 类句柄 | dlink 现在 1h **太长**（见下） |

**必做的具体修正**（本文可验证的最小集）：

1. `baidupcs.Delete` / `Move` 成功后 `invalidateDlink(srcKey)`（当前完全没做 ⇒ 删后同名重建
   可能命中旧直链）。**这是一行修复 + 一条测试**。
2. `dlink` TTL 从 1h 下调必须谨慎——但**至少**在删除路径主动失效，这样「删除后再访问」不再
   依赖 TTL。真实签名有效期 8h，1h TTL 的初衷是「先于签名到期」，与删除无关；删除失效与 TTL
   是两条独立防线，都要有。
3. `secretdata` 的**跨进程/外部改动**：当前索引只在挂载时扫一次（`loadIndex`），无任何刷新
   入口。设计取舍（**需要产品裁定**，见第六节）。

### 3.4 第四层——删除时序（用户特别关注的问题）

删除是**最容易留下陈旧副本**的动作，因为它同时改变了 A（内容没了）、C（条目没了）、D（用量
少了）。规定删除的**三段式**：

```
① 前：以什么身份/版本删（校验）
     - A 类：用「删除前现取」的 checksum（禁止用列表里的旧值直接当权威 → 但若列表值本就是
       刚取的、且我们接受「删除只防误删不防篡改」，可作为快速路径；**必须写明选了哪一种**）。
     - 当前实现：`crossCheckExternalChecksum` 用 sidecar 记录值比对（不重算）——属「防误删」，
       不是「防篡改」。文档需显式声明，避免误以为强一致。

② 中：删除本身（远端）
     - 失败 ⇒ 本地**一律不动**（不释放配额、不清缓存），保持可重试。

③ 后：失效本地派生状态（顺序不可颠倒）
     a. 内容缓存（块/窗口/明文）→ 即时清（secretdata ✔）
     b. 结构视图（索引/列表缓存）→ 即时清（search index ✔）
     c. 句柄（dlink/token）→ **新增：即时 clear key**（baidupcs ✘ → 本文修）
     d. 账本（配额/容量）→ 用**删除前实测**的字节释放（现状 ✔，注释已固化「同源口径」）
     e. 审计/事件 → 发布（现状 ✔）
     f. sidecar（trusted `.meta`）→ 随主文件删；孤儿靠 GC（现状 ✔，但要文档化「GC 前
        孤儿会占 meta 桶配额」）
```

**为什么顺序不能颠倒**：先清缓存再删远端 ⇒ 删除失败时缓存已空（性能损失但正确）；先删远端
再清缓存 ⇒ 中间窗口读到旧缓存 **但对象已不存在**（下次操作会 404，可接受）。真正危险的是
**删除成功却不失效**（幽灵存在到期）。故规则是：**③ 必须在 ② 确认成功后立即执行，且不得
因 ③ 的任何单项失败而回滚 ②**（失败要 Warn + 记指标，绝不把已删的对象「复活」到账本）。

### 3.5 删除时的「过期」语义分层（回答"如何过期"）

| 层 | 过期方式 | 理由 |
|---|---|---|
| 内容/结构/句柄 | **删除即失效**（同步、精确键） | 已确认的对象消失，没有等待理由 |
| **外部删除**（非本进程删的） | **无法即时感知** ⇒ 只能：A 类**不缓存**（每次现取）；B 类靠 TTL+失败自愈；C 类靠**定期重扫/版本探测**（需设计）；D 类靠**对账**（已有 `capacity` 对账 + 手工 `volume reconcile`） | 没有通知渠道时，唯一可靠策略是「不把不可感知的东西当权威」 |
| sidecar 孤儿 | GC（可选、后台） | 不影响正确性，只影响配额美观 |

**这条是全文最重要的结论**：*凡是**本进程之外**可能被删除的东西（外部卷、多实例共享卷、
用户直接用网盘 App 改的卷），其派生值要么不缓存，要么必须有 TTL/重扫，**不能靠"我删的时候
记得清"**。*

## 六、待裁定（阻塞 S5）

1. **secretdata 是否支持「外部侧改动后重扫」？**
   - 选项 A：不支持，**文档明确声明**「卷根目录不得被 sproxy 之外的进程修改」（当前隐含前提）。
     成本 0；风险是用户用网盘 App 动了卷 → 幽灵条目直到重启。
   - 选项 B：加显式 `sclient volume refresh <卷>`（重新 `loadIndex`，需处理并发写）。
     成本中；可控且不引入后台开销。
   - 选项 C：后台定期探测（容器数/mtime 抽样，变化则重扫）。成本高，且网盘上探测本身要 RTT。
2. **删除前置校验的口径**：继续「sidecar 记录值比对（防误删）」还是升级为「重算（防篡改）」？
   重算 = 删前整文件下载一次，对 6GiB 不可接受 ⇒ 建议维持并在 API 文档写明「checksum 门禁
   防误删、不防篡改」。

## 七、验证方式（每片都要）

- S1：单测「写入 → 取直链（填缓存）→ 删除 → 同名重建 → 断言重新签发（不复用旧 URL）」；
  变异：去掉 invalidate ⇒ 红。
- S2/S3：e2e 断言 `GET /api/files?volume=<secretdata>` 的 `files[].checksum` 非空且等于
  `HEAD stat` 的值；baidupcs 卷该字段仍为空（显式 unknown，不是 bug）。
- S4：archcheck 门禁用例（构造一个带缓存能力但不失效的假 FS ⇒ 门禁红）。
