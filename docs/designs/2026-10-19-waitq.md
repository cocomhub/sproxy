# 通用等待/排队能力（`pkg/waitq`）—— 加权 · 多资源 · 优先级 · 可扩展

> 状态：**设计（待评审后实施）**。用户裁定（2026-10-19）：
> ⑥ **队列等待能力是否有功能包提供通用能力**保证灵活复用，支持使用方扩展**内存配额等待、CPU 配额等待**等；
> ⑥′ 设计原则：**由 pkg 包提供通用能力抽象，使用方灵活扩展场景**；
> 并沿用既有裁定：**丢唤醒 = 根等待锁**（全局锁序）、**结构门禁 > 运行时竞态用例**、**禁新增 `time.Sleep`**。

---

## 1. 现状：**没有**通用能力包，有 **4 套独立实现**

| # | 实现 | 机制 | 资源 | 等待 | 超时 | 「永不可能」立即失败 | 惊群 | 队列上限 | 优先级 | 可观测 |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | `pkg/quota/wait.go`（`WaitReserve`） | `sync.Cond`（根节点） | 磁盘配额（多级） | ✓ | 30s | ✓ `canNeverFit` | ✗ `Broadcast` | ✗ | ✗ | 仅测试计数 ✗ |
| 2 | `pkg/quota/staging_tracker.go` | `sync.Cond` + `waitWatcher` | staging 磁盘 | ✓ | 5s | ✗ | ✗ | ✗ | ✗ | 仅测试计数 ✗ |
| 3 | `pkg/server/ratelimit.go`（`semaphore`） | 计数 + 通道 | 并发请求数 | ✗ 非阻塞 | — | n/a | n/a | ✗ | ✗ | ✗ |
| 4 | `golang.org/x/sync/semaphore.Weighted`（`pkg/cloud/manager_membudget.go`） | 加权信号量 | **内存字节**（校验预算） | ✓ | ctx | ✗ | ✓ FIFO | ✗ | ✗ | ✗ |

**问题**：

- **P1-a 结构孪生**：#1 与 #2 是同一套逻辑写了两遍——「根锁 double-check → 持锁广播 → `AfterFunc`/watcher 打断 → `waitRounds` 计数」逐条对应 ⇒ 任何一处修 bug 必须同步另一处（历史已出现「修了一个漏了另一个」类风险）。
- **P1-b 丢唤醒靠调用方纪律**：现有防线是**门禁 R34**（要求每个「释放/放宽」入口必须包在 `withWaitLock` 内）⇒ 新增释放入口若忘登记就会静默丢唤醒（等到超时才重试）⇒ **应当由能力包内部结构性保证**，而不是靠每个调用点自觉。
- **P1-c 惊群**：`Broadcast` 唤醒全部等待者，只 1 个能成功 ⇒ 其余重新睡；高并发上传下是锁/CPU 热点。
- **P1-d 无背压**：无队列上限 ⇒ 配额长期不足时等待者无界堆积（每请求占 goroutine ≤30s）。
- **P1-e 无优先级/公平性**：交互式小请求与后台大批量同等竞争，且 `Broadcast` 无 FIFO 保证 ⇒ 可能饿死。
- **P1-f 无可观测**：只有测试用 `waitRounds`，**无 metrics**（生产无法回答「谁在等、等多久、多少超时、队列多深」）。
- **P1-g 配额获取路径不收敛**（7 条，见 §8.2）⇒ 同一「配额不足」在不同写面表现不同（立即 507 vs 等 30s）。
- **P2**：`WaitReserve` 唯一生产调用点用 `context.Background()`（客户端断连不取消等待）。

**对照（正面范式）**：staging 侧 `StagingQuotaGateFS` **默认强制**（未实现能力接口即被门卫强制预留，fail-safe）⇒ 「默认强制 + 能力自管」正是配额/等待侧应复用的范式。

## 2. 目标与设计原则

1. **一个通用能力包** `pkg/waitq`：加权、多资源、优先级、背压、可观测、**结构性防丢唤醒**。
2. **使用方只实现 `Resource` 适配器**（磁盘/内存/CPU/带宽/连接数…）⇒ **灵活扩展**（用户要求⑥）。
3. **能力由结构体提供**（`*waitq.Queue` 注入装配），**零全局变量** ⇒ 可测、不污染其他功能测试。
4. **锁与唤醒由能力包统一**：使用方**不再**手写 `sync.Cond`/广播 ⇒ 丢唤醒从「调用方纪律」变为「库内不变式」。
5. **可测**：注入 `Clock`、确定性 `Stats()`（取代 `time.Sleep` 同步）。
6. **零回归**：现有 4 套实现先以**适配器**接入（行为逐条对照），再删除原实现。

## 3. 总体架构

```
                      ┌──────────────── pkg/waitq（通用能力，结构体）────────────────┐
 使用方（适配器）       │  Queue：FIFO + 优先级桶 + 老化提升 + 队列上限 + 指标          │
 ───────────────       │   ├─ Acquire(ctx, Request) (*Lease, error)   ← 唯一入口     │
 磁盘配额 Resource      │   ├─ 内部：canNeverFit → 立即失败（不排队）                  │
 内存配额 Resource      │   ├─ 内部：**持 q.mu** double-check → 定向唤醒（无惊群）      │
 staging Resource       │   ├─ 内部：ctx/deadline/timeout 打断（AfterFunc，无常驻 goroutine）│
 CPU 槽 Resource        │   ├─ 内部：多资源按名排序原子获取 + 失败回滚（无死锁）         │
 带宽 Resource          │   └─ Stats()/Metrics：深度/等待时长/超时/队列满               │
                       └───────────────────────────────────────────────────────────────┘
装配层：构造 Queue（注入 Clock/Metrics/默认超时/队列上限）→ 注入 quota/staging/cloud/…
```

**关键不变式（库内保证）**：

- **I1 丢唤醒不可能**：所有「可用额度变化」只能经 `Queue.Release(lease)` / `Queue.Adjust(res)` 进入，二者**必持 `q.mu`** 并唤醒等待者 ⇒ 使用方即使写错也不会丢唤醒（R34 从「门禁」降级为「冗余保险」）。
- **I2 无惊群**：唤醒时**从队首扫描**，只唤醒「当前可用额度能满足」的等待者（有界扫描 + 命中即停）。
- **I3 无忙等**：double-check 命中即返回让调用方重试（不睡）；不命中才睡。
- **I4 无死锁**：多资源按 `Resource.Name()` **字典序**获取；失败按逆序回滚。
- **I5 有界**：等待者数 ≤ `MaxWaiters`；超限立即返回 `ErrQueueFull`（调用方映射 429/507 + `Retry-After`）。
- **I6 无饿死**：优先级 + 老化（等待超 `AgeBoost` 提升有效优先级）。

## 4. API 细化

```go
package waitq

// Resource 是使用方扩展点：任何「有容量、可占用、可释放」的资源。
type Resource interface {
    Name() string                  // 唯一标识（用于多资源排序与指标标签）
    Capacity() int64               // 当前可发放上限（含运维余量折算）；0 = 无上限
    Used() int64                   // 当前已占用（含已预留）
    // TryAcquire 原子尝试获取 n：成功 nil；不足 ErrInsufficient；其它错误原样返回。
    TryAcquire(n int64) error
    // Release 释放 n。**不负责唤醒**——唤醒由 Queue 统一（I1）。
    Release(n int64)
}

type Priority int
const ( Background Priority = iota; Normal; Interactive )

type Request struct {
    Group    []Resource      // 多资源原子获取（按 Name 排序；单资源只填 1 个）
    N        int64           // 权重（字节/槽位）
    Priority Priority
    Timeout  time.Duration   // 0 ⇒ Queue 默认
    Label    string          // 指标标签（如 "quota.user" / "mem.check" / "cpu.ffmpeg"）
}

type Lease struct { /* 内部：已获取的 (resource,n) 列表 + 归还 */ }
func (l *Lease) Release()   // 幂等；归还全部资源并唤醒等待者

type Options struct {
    Clock        Clock       // 可注入（测试）
    DefaultWait  time.Duration
    MaxWaiters   int         // 0 = 不限制（不建议）
    AgeBoost     time.Duration
    Metrics      Metrics
}

type Queue struct { /* mu, waiters(FIFO+优先级), stats, clock, … */ }
func New(opts Options) *Queue
func (q *Queue) Acquire(ctx context.Context, req Request) (*Lease, error)
func (q *Queue) Stats() Stats                 // 深度/累计等待/超时/队列满（确定性，供测试同步）
func (q *Queue) Rotate(resource string) error // 容量变更（如 SetMaxBytes）后唤醒等待者（I1）

// 错误
var (
    ErrInsufficient = errors.New("waitq: 额度不足")        // 可等待
    ErrImpossible   = errors.New("waitq: 超过容量上限，永不满足") // 立即失败，不排队
    ErrQueueFull    = errors.New("waitq: 等待队列已满")      // 背压
    ErrTimeout      = errors.New("waitq: 等待超时")
)
```

**调用方语义**：`Acquire` 返回 `*Lease` 后，业务完成时 `lease.Release()`；`ErrImpossible/ErrQueueFull/ErrTimeout` 分别映射 507 / 429 / 507（+`Retry-After`）。

## 6. 边界场景（逐条）

| # | 场景 | 处理 |
|---|---|---|
| W1 | 释放与等待交错（丢唤醒） | I1：释放必持 `q.mu` + double-check 后睡 |
| W2 | 惊群 | I2：队首定向唤醒（有界扫描） |
| W3 | 请求 > 任何容量 | `ErrImpossible` **立即失败**（不白等满超时；沿用 `canNeverFit` 语义） |
| W4 | ctx 取消 / 客户端断连 | `AfterFunc` 打断（**无常驻 goroutine**）；调用方传请求 ctx（**禁 `context.Background()`**） |
| W5 | 超时 | `Request.Timeout` 与 ctx deadline 取较早者；`ErrTimeout` |
| W6 | 队列满 | `ErrQueueFull` + `Retry-After`（背压，不堆积 goroutine） |
| W7 | 多资源部分成功 | 逆序回滚（不留半入账） |
| W8 | 多资源加锁顺序 | 按 `Name()` 字典序（防死锁） |
| W9 | 同 goroutine 重入（持有 lease 再 Acquire 同资源） | **文档禁止** + `Queue` 记录持有者标签，检测到自等待 ⇒ 立即报错（fail-fast，防自锁死） |
| W10 | 优先级饿死 | 老化提升 |
| W11 | 容量变更（`SetMaxBytes`/`Adjust`/卷卸载） | `Queue.Rotate(res)` 唤醒（**取代**「每个释放入口都要包 `withWaitLock`」的门禁纪律） |
| W12 | 释放多于获取（计数下溢） | `Resource.Release` 契约：下溢 panic/报错（fail-fast，暴露调用方 bug） |
| W13 | 关闭/停机 | `Queue.Close()`：唤醒全部等待者并返回 `ErrClosed`（不泄漏 goroutine） |
| W14 | 指标高基数 | `Label` 受控枚举（门禁：只允许登记过的 label） |
| W15 | 时钟回拨 | 老化判定用单调时钟（`Clock` 提供 `Since`） |
| W16 | 大 `MaxWaiters` 下的内存 | 等待者节点池化/上限（有界内存） |

### 8.1 迁移步骤

| 步骤 | 内容 |
|---|---|

| 门禁 | 断言 |
|---|---|
| **R36-a** | 非测试源码**禁**直接调用 `TryReserve`/`WaitReserve`/`semaphore.Weighted`（白名单：`pkg/waitq` 与适配器）⇒ 棘轮只减不增 |

## 11. 风险与开放问题

| # | 项 | 建议 |
|---|---|---|
| O1 | 默认超时 | 沿用现状：配额 30s、staging 5s；新资源显式登记（禁隐式默认） |
| O2 | `MaxWaiters` 默认值 | 建议按资源登记（如 `quota`=1000）；0=不限 ⇒ 不推荐 |
| O3 | 是否保留 R34 门禁 | 建议保留为**冗余保险**，待 I1 稳定一版后退役 |
| O4 | `ratelimit` 并发槽是否迁移 | 可选（其语义是非阻塞；接入主要为指标统一） |
| O5 | 优先级是否暴露到配置 | 建议内部常量先落地（`Interactive/Normal/Background`），需要再配置化 |
