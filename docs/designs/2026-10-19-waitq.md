# 通用等待/排队能力（`pkg/waitq`）—— 加权 · 多资源 · 优先级 · 可扩展

> 状态：**设计 v2（经 3 路独立 fresh-context 对抗审核并逐条证伪后修订；待你确认后实施）**。
> 用户裁定（2026-10-19）：⑥ 队列等待能力**是否有功能包提供通用能力**、保证灵活复用，
> 支持使用方扩展**内存配额等待、CPU 配额等待**等；⑥′ 设计原则：**pkg 提供通用能力抽象，
> 使用方灵活扩展场景**。沿用既有裁定：**丢唤醒 = 根等待锁**、**结构门禁 > 运行时竞态用例**、
> **禁新增 `time.Sleep`**、**唯一实现**。

## 1. 现状：**没有**通用能力包，有 **4 套独立实现**

| # | 实现 | 机制 | 资源 | 等待 | 超时 | 「永不可能」立即失败 | 惊群 | 队列上限 | 优先级 | 可观测 |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | `pkg/quota/wait.go`（`WaitReserve`） | `sync.Cond`（根节点，`quota.go:46`） | 磁盘配额（多级） | ✓ | 30s | ✓ `canNeverFit` | ✗ `Broadcast` | ✗ | ✗ | 仅测试计数 ✗ |
| 2 | `pkg/quota/staging_tracker.go` | `sync.Cond` + `waitWatcher`（`staging_tracker.go:35`） | staging 磁盘 | ✓ | 5s | ✗ | ✗ | ✗ | ✗ | 仅测试计数 ✗ |
| 3 | `pkg/server/ratelimit.go`（`semaphore`） | 计数 + 通道 | 并发请求数 | ✗ 非阻塞 | — | n/a | n/a | ✗ | ✗ | ✗ |
| 4 | `golang.org/x/sync/semaphore.Weighted`（`pkg/cloud/manager_membudget.go`） | 加权信号量 | **内存字节**（校验预算） | ✓ | ctx | ✗ | ✓ FIFO | ✗ | ✗ | ✗ |

**问题**：

- **P1-a 结构孪生**：#1 与 #2 是同一套逻辑写了两遍（根锁 double-check → 持锁广播 → 定时/ctx 打断 → `waitRounds` 计数）⇒ 修一处必须同步另一处。
- **P1-b 丢唤醒靠调用方纪律**：现有防线是**登记式门禁 R34**（`quota_waitlock.tsv` 登记 11 个释放入口，断言其方法体含 `withWaitLock(`）——**新增未登记入口不会被拦** ⇒ 应升级为**库内结构性保证**（但见 P1-e）。
- **P1-c 惊群**：`Broadcast` 唤醒全部等待者，只 1 个成功 ⇒ 其余重新睡（高并发上传下是锁/CPU 热点）。
- **P1-d 无背压**：无队列上限 ⇒ 配额长期不足时等待者无界堆积（每请求占 goroutine ≤30s）。
- **P1-e 无可观测**：只有测试用 `waitRounds`，**无 metrics**（生产无法回答「谁在等、等多久、多少超时、队列多深」）。
- **P1-f 获取路径不收敛（审核订正：**实测 ~40 处、且是**两层**）**：
  - **层 A（配额）**：`quota.Scope/Pool.TryReserve` —— `files/options.go:428`、`files/dir_charge.go:64,72`、`files/version_store.go:184,191`、`files/write_ops.go:1276,1523`、`files/chunked_upload.go:490`（经 `TryReserveChunked` 适配器）、`volume/registry/quota_volume.go:238,258`、`volume/capacity/ledger.go:1103`、`server/volumes.go:654`、`server/volumes_api.go:516,523,634,641`、`server/volumes_mirror.go:310,317`、`server/version.go:357,369`、`server/files_service.go:1128`、`server/s3_part_ledger.go:86,93`、`server/sync_handler.go:59`、`server/cloud_download_handler.go:828`、`server/backup_api.go:438,445`、`syncexec/executor.go:209`、`cloud/manager_task.go:81`（探测式）、`cloud/transfer.go:871`（探测式）、`quota/staging_tracker.go:76,101,110`；
  - **层 B（容量管理）**：`storage/capacity.Manager.TryReserve(cat)` —— `server/backup_api.go:409,478`、`server/cloud_archive_handler.go:467`、`server/cloud_download_handler.go:837,893`、`server/cloud_service.go:24`、`server/sync_handler.go:38`、`server/files_service.go:48`、`syncmgr/manager.go:551,1228`；
  - **等待只覆盖 1 条**（`server/volumes.go:572,628`，且用 `context.Background()`）⇒ 同一「不足」在不同写面表现不同（立即失败 vs 等 30s）。
- **P2**：`WaitReserve` 生产调用点**恰 2 处**（`volumes.go:572/628`），**均**用 `context.Background()`（客户端断连不取消等待）。

**对照（正面范式）**：staging 侧 `StagingQuotaGateFS` **默认强制**（未实现能力接口即被门卫强制预留，fail-safe）⇒ 这正是配额/等待侧应复用的范式。

## 2. 目标与设计原则

1. **一个通用能力包** `pkg/waitq`：加权、多资源、优先级、背压、可观测。
2. **使用方只实现 `Resource` 适配器**（磁盘/内存/CPU/带宽/连接数）⇒ **灵活扩展**（用户要求⑥）。
3. **结构体能力**（`*waitq.Queue` 注入装配），**零全局可变状态** ⇒ 可测、不污染其他功能测试。
4. **锁与唤醒由能力包统一**：使用方不再手写 `sync.Cond`/广播。
5. **可测**：注入 `Clock`（`Now` + `Since`）、确定性 `Stats()`（取代 `time.Sleep` 同步）。
6. **零回归**：现有 4 套实现先以**适配器**接入（行为逐条对照），再删原实现。

## 3. 总体架构

```
                      ┌──────────────── pkg/waitq（通用能力，结构体）────────────────┐
 使用方（适配器）       │  Queue：FIFO + 优先级桶 + 老化提升 + 队列上限 + 指标          │
 ───────────────       │   ├─ Acquire(ctx, Request) (*Lease, error)   ← 唯一入口     │
 层 A 配额 Resource     │   ├─ 内部：canNeverFit → 立即失败（不排队）                  │
 层 B 容量 Resource     │   ├─ 内部：**持 q.mu** double-check → 定向唤醒（无惊群）      │
 staging Resource       │   ├─ 内部：ctx/deadline/timeout 打断（AfterFunc，无常驻 goroutine）│
 内存 Resource          │   ├─ 内部：多资源按名排序原子获取 + 失败回滚（无死锁）         │
 CPU 槽 Resource        │   ├─ Notify(res)：**释放侧统一入口**（见 §3.1 I1）            │
 带宽 Resource          │   └─ Stats()/Metrics：深度/等待时长/超时/队列满               │
                       └───────────────────────────────────────────────────────────────┘
装配层：构造 Queue（注入 Clock/Metrics/默认超时/队列上限）→ 注入 quota/staging/cloud/…
```

### 3.1 关键不变式（**含审核修订**）

- **I1 丢唤醒防护（修订：必须由释放侧配合，库不单独保证）**
  **原表述「使用方即使写错也不会丢唤醒」不成立** ✗（审核 P1）：`pkg/quota` 的释放入口广播的是**它自己的 `root.cond`**，不持有 waitq `Lease` ⇒ 迁移后等待者睡在 waitq 队列上，**收不到唤醒**（比现状更坏）。
  **修订后的机制**：`pkg/quota` 的每个释放/放宽入口（`quota_waitlock.tsv` 登记的 11 个）在**既有 `withWaitLock` 内追加** `queue.Notify(resource)`（或 `Queue.Adjust(res)`）；R34 门禁的断言由「含 `withWaitLock(`」升级为「含 `withWaitLock(` **且** 含 `Notify(`/`Adjust(`」⇒ 结构门禁仍然锁死，但保证的是**正确的队列**。适配器定义到具体文件（R36-a 白名单）。
- **I2 无惊群**：唤醒时**从队首扫描**，只唤醒「当前可用额度能满足」的等待者（有界扫描 + 命中即停）。
- **I3 无忙等**：double-check 命中即返回让调用方重试（不睡）。
- **I4 无死锁**：多资源按 `Resource.Name()` **字典序**获取；失败按逆序回滚。
- **I5 有界**：等待者数 ≤ `MaxWaiters`；超限立即 `ErrQueueFull`（调用方映射 429 + `Retry-After`）。
- **I6 无饿死**：优先级 + 老化（等待超 `AgeBoost` 提升有效优先级）。

## 4. API 细化（**含审核修订**）

```go
package waitq

type Resource interface {
    Name() string                  // 唯一标识（多资源排序 + 指标标签；须登记，见 R36-c）
    Capacity() int64               // 当前可发放上限（含运维余量折算）；0 = 无上限
    Used() int64                   // 当前已占用（含已预留）
    TryAcquire(n int64) error      // 原子尝试：不足 ⇒ ErrInsufficient；其它错误原样返回
    Release(n int64)               // 释放（**不负责唤醒**；唤醒经 Queue.Notify，见 I1）
}

type Priority int
const ( Background Priority = iota; Normal; Interactive )

type Request struct {
    Group    []Resource      // 多资源原子获取（按 Name 排序；单资源填 1 个）
    N        int64           // 权重（字节/槽位）
    Priority Priority
    Timeout  time.Duration   // 0 ⇒ Queue 默认
    Label    string          // 指标标签（受控枚举，见 R36-c）
    Holder   string          // **（审核 W9）持有者标识**：用于「同资源重入 ⇒ 立即报错」检测
}

type Lease struct { /* 已获取的 (resource,n) 列表；Release 幂等 */ }
func (l *Lease) Release()

type Clock interface {           // 与 pkg/audit 同一契约（审核：原文档只引用未定义）
    Now() time.Time
    Since(time.Time) time.Duration
}

type Options struct {
    Clock       Clock
    DefaultWait time.Duration
    MaxWaiters  int
    AgeBoost    time.Duration
    Metrics     Metrics
}

type Queue struct { /* mu, waiters(FIFO+优先级), stats, clock, holders, … */ }
func New(opts Options) *Queue
func (q *Queue) Acquire(ctx context.Context, req Request) (*Lease, error)  // 唯一入口
func (q *Queue) Notify(res Resource)                                       // **释放侧统一入口**（I1）
func (q *Queue) Stats() Stats                                              // 确定性（测试同步用）
func (q *Queue) Close() error                                              // 唤醒全部等待者（ErrClosed）

var (
    ErrInsufficient = errors.New("waitq: 额度不足")            // 可等待
    ErrImpossible   = errors.New("waitq: 超过容量上限，永不满足")  // 立即失败，不排队
    ErrQueueFull    = errors.New("waitq: 等待队列已满")          // 背压
    ErrTimeout      = errors.New("waitq: 等待超时")
    ErrReentrant    = errors.New("waitq: 同资源重入等待（自锁死）")
    ErrClosed       = errors.New("waitq: 队列已关闭")
)
```

## 6. 边界场景（W1–W18）

| # | 场景 | 处理 |
|---|---|---|
| W1 | 释放与等待交错（丢唤醒） | I1：释放侧经 `Notify`（持 `q.mu`）+ 等待侧 double-check 后睡 |
| W2 | 惊群 | I2：队首定向唤醒（有界扫描） |
| W3 | 请求 > 任何容量 | `ErrImpossible` 立即失败（沿用 `canNeverFit` 语义） |
| W4 | ctx 取消 / 客户端断连 | `AfterFunc` 打断（无常驻 goroutine）；**调用方必须传请求 ctx**（禁 `context.Background()`；`volumes.go:572/628` 一并修） |
| W5 | 超时 | `Request.Timeout` 与 ctx deadline 取较早者 ⇒ `ErrTimeout` |
| W6 | 队列满 | `ErrQueueFull` + `Retry-After`（背压，不堆积 goroutine） |
| W7 | 多资源部分成功 | 逆序回滚（不留半入账） |
| W8 | 多资源加锁顺序 | 按 `Name()` 字典序（防死锁） |
| W9 | 同 goroutine 重入（自锁死） | **`Request.Holder`** + 持有者集合 ⇒ `ErrReentrant` fail-fast（审核修订：原设计无抓手） |
| W10 | 优先级饿死 | 老化提升（`Since` 单调） |
| W11 | 容量变更（`SetMaxBytes`/`Adjust`/卷卸载） | `Queue.Notify(res)`（**取代**「每个释放入口自行 `withWaitLock`」的旧纪律） |
| W12 | 释放多于获取（下溢） | `Resource.Release` 契约：下溢报错/panic（fail-fast）——**实施前须核查既有 `Release` 的 defer/异常路径无双释放**（审核提醒） |
| W13 | 关闭/停机 | `Close()` 唤醒全部并返回 `ErrClosed`（不泄漏 goroutine） |
| W14 | 指标高基数 | `Label` 受控枚举（R36-c 登记） |
| W15 | 时钟回拨 | 老化/过时用 `Clock.Since`（单调） |
| W16 | 大 `MaxWaiters` 内存 | 等待者节点有界（上限即界） |
| **W17** | **迁移期双队列**（等待者在 waitq、释放方广播旧 cond） | **禁止**：适配器迁移必须**同一提交内**完成「等待侧改 `Acquire` + 释放侧改 `Notify`」，否则比现状更坏（审核 P1）；补「迁移后不丢唤醒」回归用例 |
| **W18** | **两层预留**（层 A 配额 + 层 B 容量管理） | 同一 `Request.Group` 原子获取两侧（§8.2），失败逆序回滚 ⇒ **不留半入账**（审核订正） |

## 7. 使用方扩展示例（灵活复用）

| 场景 | `Resource` 适配器 | 权重 | 备注 |
|---|---|---|---|
| **磁盘配额（层 A）** | `quotaResource{scope/pool}`（多级 ⇒ `Group`） | 物理/逻辑字节 | 替换 `WaitReserve` 内部实现，对外 API 不变 |
| **容量管理（层 B）** | `capacityResource{manager, category}` | 字节 | 与层 A 组成 `Group` ⇒ 与现状双预留语义一致 |
| **staging 磁盘** | `stagingResource{tracker}` | 字节 | 超时 5s ⇒ `Request.Timeout` |

| **CPU 配额** | `cpuResource{name:"cpu.ffmpeg", slots:N}` | 槽位 | 重任务限并发，可给 `Interactive` |
| **带宽/连接数** | 同上 | bps / 计数 | 出口限速、隧道并发 |

## 9. 测试计划

| 类别 | 用例 |
|---|---|
| 基础 | 立即获取 / 不足等待 / 释放唤醒 / 超时 / ctx 取消 |
| 不变式 | **丢唤醒**（并发释放+等待，断言无空等）· **惊群**（N 等待者释放 1 份 ⇒ 只唤醒 1 个）· **忙等** · **死锁**（多资源乱序） |
| 边界 | `ErrImpossible` 立即失败（断言耗时 < 阈值）· `ErrQueueFull` · **重入 `ErrReentrant`** · 下溢 fail-fast · `Close` 唤醒全部 |
| 公平 | 优先级顺序 · 老化（`Background` 久等后提升） |
| 可测性 | 注入 Clock（`Since`）驱动老化/超时，**零 `time.Sleep`** |
| 隔离 | 两个 Queue 互不影响（无全局可变状态） |
| 迁移等价 | 对 #1/#2/#4 逐条对照（超时值、错误映射、`canNeverFit`、并发不变量）+ **W17「等待侧+释放侧同提交」回归** |

## 11. 开放问题

| # | 项 | 建议 |
|---|---|---|
| O1 | 默认超时 | 沿用现状：配额 30s、staging 5s；新资源显式登记（禁隐式默认） |
| O2 | `MaxWaiters` 默认 | 按资源登记（如 `quota`=1000）；0=不限 ⇒ 不推荐 |
| O3 | R34 门禁升级后是否退役 | 升级为「须 `Notify`」后**保留**（结构保证），不退役 |
| O4 | `ratelimit` 并发槽是否迁移 | 可选（语义非阻塞；接入主要为指标统一） |
| O5 | 优先级是否配置化 | 先内部常量（`Interactive/Normal/Background`），需要再配置化 |
| **O6** | **探测式 `TryReserve`（cloud 两处）** | 建议保留为「校验型、不排队」并登记豁免（语义与排队不同） |
| **O7** | **层 B（容量管理）是否本期收敛** | 建议**是**（组成 `Group` 才不留半入账）；若分期，须明确「本期只收敛层 A」并保留 R36-a 豁免 |
