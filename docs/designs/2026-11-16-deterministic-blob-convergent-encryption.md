# 确定性分块与收敛加密（secretdata 卷重复上传零重复、秒传可命中）

> 状态：**设计待审**（2026-11-16）。决策人：用户（已确认接受"收敛加密"的取舍）。
> 关联：`pkg/cryptox/shardseal`（分块/加密/派生）、`pkg/volume/secretdata`（写路径）、
> 网盘后端 `pkg/volume/ext/baidupcs`（秒传/极速上传）。

## 1. 问题（实测证据）

上传**同一个** 6.08 GiB 视频到 `baidu`（secretdata over baidupcs）卷，多次/多轮后：

| 指标 | 单轮应有 | 实际观测 | 倍数 |
| --- | --- | --- | --- |
| 容器内 blob 数 | **68**（日志 `bad=68 of=68`） | **165** | 2.4× |
| 容器体积 | 6.08 GiB | **13.88 GiB** | 2.3× |
| 文件时间戳 | 单簇 | **三簇**（12:09 / 13:53 / 15:23） | 多轮 |

**后果**：
1. **空间浪费**（2.3× 孤儿 blob 常驻网盘）；
2. **秒传永不命中**——百度侧以**内容哈希**判去重，密文每次都不同 ⇒ 服务端永远认为"是新文件" ⇒
   重传/重试都是**全量传输**（实测 6 GiB 传了 ~4 小时，期间 `上传内核失败…获取 uk 失败（需 STOKEN）`
   反复降级到慢路径）；
3. **校验必然失败**——写入预期（本地密文摘要）与远端实际内容无法稳定对齐，出现 `bad=68/68` 并进入
   整文件重试死循环。

## 2. 现状根因（两处**随机**，均在写路径上）

blob 名**已是内容寻址**（`pkg/cryptox/shardseal`：`chunkBlobNameAndWrite` → `ChunkName(Hash48Pair(密文), group)`），
**名字不同不是因为命名随机，而是因为密文本身每次不同**。随机源有两处：

| # | 位置 | 现状 | 影响 |
| --- | --- | --- | --- |
| ① **分块范围** | `pkg/cryptox/shardseal/block.go` 的 `RandomPlanner`（`cryptoRandN`，**1MB–200MB 随机**） | 每次加密的**块边界都不同** | 块数量/偏移/名字全变 ⇒ 对象集合不可能复用 |
| ② **每块 salt / nonce / 随机首部** | `RandSalt()`（`meta_blob.go`）、每段**随机 12B nonce**（`crypto.go`，格式 `[R 128B 随机首部][8B 密文长][salt][nonce][ct+tag]`） | 相同明文的**密文不同** | blob 名（密文哈希）不同 ⇒ 新对象 + 旧对象成孤儿 |

⇒ **两者都确定性化**，才能让"同一明文 ⇒ 同一密文 ⇒ 同一 blob 名 ⇒ 同一对象"成立。

## 3. 设计

### 3.1 派生源：**内容标识**（不用文件名/路径）

派生输入统一取**内容摘要**，**不取可变的名字/路径**：

```
CID  = SHA-256(明文整文件)                      # 内容标识（与文件名/mtime/路径无关）
```

> 理由（用户明示）：文件名/路径可变（改名/移动/跨路径拷贝），用它派生会让"同一内容"产生不同密文，
> 违背"同一文件一定一致"的目标。取内容哈希后，**同一内容在任何路径/任何名字下都产生同一密文**，
> 天然获得**跨路径去重**能力。

**派生函数**（卷密钥 `K` 为输入，`ver` 为算法版本）：

```
derive(K, label, CID, i) = HMAC-SHA256(K, "sdconv1" ‖ label ‖ CID ‖ u64be(i))
```

- `label ∈ {blockplan, salt, nonce, header, blockletplan}`
- `i` = 块序号 / blocklet 序号（无二级序号时取 0）

### 3.2 分块范围确定性化

`RandomPlanner` 的"变长"特性**保留**（变长本身有安全价值），但长度改为**确定性派生**而不是 `crypto/rand`：

```
blockLen_i = minLen + (derive(K,"blockplan",CID,i) mod (maxLen-minLen+1))
```

- 边界序列由 `(K, CID, i)` 唯一决定 ⇒ 同一文件每次规划**完全一致**；
- 仍与内容相关（不同文件长度分布不同），**不退化为定长分块**（定长会让"块边界 = 偏移"形成可预测模式）；
- `BlockletPlanner` 同理：`fixed` 本就确定；`video-keyframe` 由内容（关键帧）决定，**天然确定** ✅。

### 3.3 salt / nonce / 随机首部确定性化

```
salt   = derive(K,"salt",   CID, i)[0:SALT_LEN]
nonce  = derive(K,"nonce",  CID, i)[0:12]
header = derive(K,"header", CID, i)[0:128]
```

⇒ 同一 `(K, CID, i)` ⇒ **逐字节相同的密文** ⇒ 相同 blob 名 ⇒ **覆盖同一对象** ⇒ 网盘侧内容哈希相同 ⇒ **秒传命中（零传输）**。

## 4. 安全分析（**必须明确接受的取舍**）

| 性质 | 结论 |
| --- | --- |
| **nonce 复用** | ✅ **安全**。nonce 输入含 **CID**（内容哈希）与块序号 ⇒ "同 key 同 nonce" 只可能出现在**完全相同的内容**上 ⇒ 不构成 GCM 的 nonce 复用攻击（复用条件是"同 key+nonce 加密**不同**明文"）。 |
| **同内容重复加密** | ✅ 安全：同 `(K, CID, i)` ⇒ 同明文 ⇒ 同密文，不新增泄露。 |
| ⚠️ **泄露"内容相等"** | **确定性/收敛加密的固有代价**：持有密文者可判断"两份是否相同内容"。**本场景已明示接受**（单用户加密卷，目标即去重/秒传；且 blob 名本就由**密文哈希**派生，对"密文相等"已然敏感）。 |
| **密钥隔离** | 不同卷/不同密钥 ⇒ 同内容密文不同 ⇒ **跨卷不可比对** ✅。 |
| **完整性** | 仍为 AES-GCM（AEAD），每段认证；确定性只改 nonce/盐的**来源**，不改认证语义 ✅。 |

## 5. 兼容与迁移

- 走**新算法版本**（复用既有 `AlgoVersion` 机制），**不改老版本语义**：老 blob 仍可解（读路径按版本分派）。
- 新写入默认使用新版本；**已有老版本文件可选惰性重加密**（读时或后台任务，**非必须**）。
- 卷的 `Options.Algorithm` 可显式指定；默认值需 `SetDefaults` 语义安全（默认即启用新版本，见 AGENTS 配置默认值纪律）。

## 6. 验收判据（硬）

1. **确定性**：同一文件两次加密 ⇒ **blob 名集合与密文逐字节相同**（单测直接断言）。
2. **零重复**：同一文件重复上传两轮 ⇒ 容器内**对象数不增加**（不产生孤儿）。
3. **秒传命中**：第二轮上传到网盘后端**零字节传输**（以 `block_list`/后端指标断言，允许旧后端降级为"覆盖写"）。
4. **幂等**：重复上传后**批量校验一致**（不再出现 `bad=N/N`）。
5. **跨路径**：同一内容放在两个不同逻辑路径 ⇒ 密文相同（按设计）。
6. **向后兼容**：老版本 blob 仍可正常读回（回归用例）。
7. **安全回归**：不同 `CID` ⇒ 不同 `salt/nonce/header`（断言不相等）；不同卷密钥 ⇒ 同内容密文不同。
8. **变异验证**：去掉任一确定性派生（改回随机）⇒ 上述 1/2/3 用例**红**。

## 7. 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| crypto 改动引入**读不回** | 新版本独立分派 + 老版本回归用例；**不做原地重写** |
| 确定性导致**跨文件信息泄露**（相等性） | 已明示接受；文档记录（本节 §4） |
| 迁移期**双版本并存** | 读路径按版本分派；写路径统一新版本；重加密为可选 |
| 实施面较大 | 分阶段：**① 确定性派生（本设计）** → ② 可选重加密 → ③ 迁移与清理孤儿 |
