## §0 为什么要先纠正表述（本次审核最重要的产出）

此前（含设计 §12）把片 7 描述为「**跨进程配额不可见** ⇒ 多节点各自记账 ⇒ 可超限」。
逐条取证后发现该表述**只对了一半**，而**错的那一半会导致错误设计**：

| 取证点 | 事实 | 证据 |
|---|---|---|
| `pkg/quota` 是否持久化 | **包内确实零持久化**（`committed`/`reserved`/`allocated` 纯内存） | `quota.go:22-27`、全包无 Load/Save |
| 卷级容量是否持久化 | **已持久化**（配置外部卷 + 用户卷） | `volumes.go:310` `capacity.NewPoolCounterPersistent`；`capacity.go:75-79`（`VolumeCapacityCounter`，原子 tmp+rename，`<root>/<owner>/meta/volume/<name>.capacity`） |
| 重启后是否归零 | **不归零**：启动/周期**对账**把 scope 校准到磁盘实际 | `quota_reconcile.go:22-38`（`reconcileQuotaScopes` → `Adjust(Usage(), diskSize)`） |
| 是否已有可观测面 | **有**：快照损坏计数 + 指标 | `capacity.go:47-55`（`CorruptSnapshotCount`）、`volumes.go:314` |

⇒ **纠正后的缺陷表述**（分场景，才是可设计的）：

| 场景 | 现状 | 是否缺陷 |
|---|---|---|
| 单进程 + 重启 | 启动对账自磁盘收敛 | ✅ 不缺陷（已有机制） |
| **单机多进程 / 多节点共享同一外部卷** | 各进程内存账本**互不可见**；卷级上限**有**持久化（文件计数）但**读-改-写非跨进程原子** ⇒ 并发可**丢失更新**；**用户/桶 scope** 完全无持久化 ⇒ **可超限** | 🔴 **真缺陷** |
| 多节点各自本地卷 | 各节点**自有磁盘** ⇒ 各自记账**本就正确**（卷 = 节点） | ✅ 不缺陷 |

**⇒ 真正的缺陷是**：**共享卷（外部/集群卷）上的「用户/桶/目录」级配额跨进程不可见 + 卷级文件计数跨进程非原子**。
**⇒ 设计必须只解决这个**（而不是「给所有配额加落盘」——那会在本地卷上付出无收益的 fsync 代价）。

## §1 代码审核结论（现状事实表）

### §1.1 账本模型（`pkg/quota`，通用领域包，零仓内依赖）
- `Pool{committed, reserved, allocated, maxBytes, parent, children, mu}`（`quota.go:22-27`）；
- 可用额度 = `maxBytes − (committed + reserved)`；占用经 `adjustUp` **沿父链聚合**（同一字节只在父池计一次）；
- `Scope` 是「路径化子作用域」，`EnsureScope(segs, limit)` 逐级建子池；
- `Reservation` 句柄：`Commit(n)` / `Release()`（原子至多一次）；
- **包内无任何持久化、无任何跨进程协调**（设计使然：通用领域模型）。

### §1.2 卷级容量（`pkg/volume/capacity`，**已有持久化**）
- `Counter` 接口：`TryAdd`（超限 fail-closed 且**不部分写入**）/`Release`/`Used`/`Capacity`；
- `VolumeCapacityCounter`（用户卷）：文件态持久化，原子 tmp+rename，损坏 ⇒ 计入 `corruptSnapshots` + 重置；
- `PoolCounter` / `NewPoolCounterPersistent`（配置外部卷）：复用卷容量 `quota.Pool`（**路由/指标/对账同源**）+ 持久化；
- `CapacityFS`：`sync.FS` 装饰器（覆盖写差分 + 透传可选能力 + 变更后持久化）。

### §1.3 对账（`pkg/server/quota_reconcile.go`，**已有**）
- `ScanAndRecalculate` 按租户桶归集磁盘字节 → `reconcileQuotaScopes` → 先深后浅 `scope.Adjust(Usage(), diskSize)`；
- **双计保护**：键上有在途预留（`Reserved>0`）或子层已 skip ⇒ 本键及前缀祖先 skip；
- **已记录的已知弱点**（源码注释自陈）：读-修正两拍**非原子** ⇒ 与写路径并发时可能欠校/过校 ⇒ 由**下次扫描自愈**。

### §1.4 装配点（现状）
| 池 | 位置 | 持久化 |
|---|---|---|
| `globalPool`（全局兜底） | `routes_setup.go:73` | ✗ |
| 卷容量池（配置卷/用户卷） | `volumes.go:269/295/304` | **✓**（外部卷）/ 用户卷走 `VolumeCapacityCounter` |
| 封装卷继承池 | `volumes_enclosure.go:91`、`nested_enclosure.go:337` | 继承源卷（✗ 自身） |
| **owner/bucket/目录 scope** | `handlers.go:757` `EnsureScope` | **✗** |
| staging 池 | `handlers.go:876` | ✗ |

## §2 缺陷的**可判定**表述（设计目标）

> **在多个 sproxy 进程共享同一外部/集群卷时，用户/桶级配额的可用额度判定必须仍然成立**
> （所有进程在同一卷上对同一用户的占用之和 ≤ 该用户在该卷的配额），
> **且不得要求各进程串行**（可用性优先），**且本地卷不得为此付出额外 I/O 代价**。

**反例（可判定的失败）**：两进程 P1/P2 共享卷 V，用户 alice 在 V 上配额 10GB，当前已用 9GB。
P1、P2 各写 1GB ⇒ 现状：两者各自认为「9+1 ≤ 10」⇒ 都成功 ⇒ 实际 11GB ✗ **超限**。

## §3 目标架构（正确 + 完整）

### §3.1 三条设计原则（每条都对应一个被否决方案）

| 原则 | 为什么 | 被否决的方案 |
|---|---|---|
| **P1 只对「共享卷」持久化** | 本地卷 = 节点自有磁盘 ⇒ 内存账本**本就正确**；落盘只增 I/O 无收益 | 「所有配额统一落盘」✗（本地卷白付 fsync，且引入无谓一致性面） |
| **P2 跨进程**只做**无协调**的合并（append-only 分片），**不做**锁/事务 | 共享卷上做「跨进程原子读-改-写」需要分布式锁 ⇒ 引入新依赖 + 可用性下降 | 「文件锁 + 读改写」✗（POSIX 锁跨节点不可靠；NFS/S3 语义不一致） |
| **P3 对账是**最终**权威**，账本是**加速器** | 已有 `reconcileQuotaScopes`（磁盘为准）；账本只用于**在途期间**的快速判定 | 「账本即权威」✗（崩溃/丢失更新 ⇒ 永久错账，不可自愈） |

### §3.2 核心形态：**分片日志账本（per-writer shard ledger）**

```
<volume>/<owner>/meta/quota/
  ├── shard.<node-id>.<epoch>.log     # 本进程 append-only 增量（TryAdd=+, Release=-）
  └── snapshot.<node-id>.json         # 本进程定期压缩后的基线（可选，控制重放成本）
```

- **写**：本进程只 append **自己的** shard（`O_APPEND` 单写者 ⇒ **无需锁**）；
- **读**（判定可用额度）：`used = Σ_shards (snapshot + log)` ⇒ 每个进程看到的都是**全局和**；
- **压缩**：本进程把自身 shard 折叠进自身 snapshot（仍只动自己的文件）；
- **回收**：进程退出/崩溃恢复后，其 shard 由**对账**折算：对账完成后可删除**已折入快照且 epoch 过期**的 shard；
- **损坏/不可读**：该 shard **跳过并计数**（`CorruptLedgerCount` 指标 + 告警）⇒ 退回对账路径（fail-safe，而非 fail-open ✗）。

**为什么这是「正确且完整」**：
- **无协调**（P2 ✓）：每个进程单写自己的文件 ⇒ 无分布式锁、无丢失更新；
- **崩溃安全**（P3 ✓）：崩溃只丢「未 flush 的增量」⇒ 对账兜底 ⇒ **不会永久少计**；
- **可观测**（既有约定 ✓）：损坏计数 + 跳过计数进指标（与 `CorruptSnapshotCount` 同型）；
- **零本地卷代价**（P1 ✓）：`kind` 为本地时**不启用**该装饰器（走纯内存，零 I/O）。

### §3.3 接线形态（复用既有接缝，不新增全局态）

```
quota.Pool ──► LedgerPool（新，pkg/quota 或 pkg/volume/capacity 层）
                 ├─ 本地卷：直通（零 I/O）
                 └─ 共享卷：TryReserve/Commit/Release 时 append 本进程 shard
                            可用额度判定 = maxBytes − (Σ_shards + reserved)
```

- **落在哪一层**：`pkg/volume/capacity`（**已有** `Counter`/`CapacityFS`/`PoolCounter` + 持久化范式 + 损坏指标）
  ⇒ 扩展该包，**不**改 `pkg/quota`（保持其「通用领域模型、零 I/O」定位）；
- **如何区分共享/本地**：用**既有**的卷类型判定（`registry.KindOf`）——**不新增配置开关**
  （避免「忘配即静默降级」✗，符合本项目「安全/限额开关必须可观测」的既有裁定）；
- **owner/bucket scope 的持久化**：`EnsureScope` 建 scope 时**按所在卷**决定是否挂 ledger
  （同一个 owner 在不同卷上可有不同策略：本地卷内存、共享卷 ledger）。

### §3.4 与既有机制的关系（**不重复造**）

| 既有机制 | 本设计如何用它 |
|---|---|
| `capacity.Counter` / `VolumeCapacityCounter` / `NewPoolCounterPersistent` | **沿用**：卷级计数已是「单文件 + tmp/rename」形态；本设计把「多进程」从「单写者」推广到「**分片多写者**」 |
| `CorruptSnapshotCount` + 指标 | **沿用范式**：新增 `CorruptLedgerCount` / `LedgerShardsSkipped` |
| `reconcileQuotaScopes`（磁盘为准 + 双计保护 + skip 传播） | **保留为最终权威**；新增「对账后回收已折入快照的过期 shard」 |
| `CapacityFS`（装饰器 + 覆盖写差分 + 能力透传） | **沿用装饰器形态**（新增 ledger 装饰器时**必须透传全部可选能力**——本项目已因「能力静默丢失」吃过一次自伤） |

## §4 关键设计决策（含理由与代价）

| # | 决策 | 理由 | 代价 / 残余风险 |
|---|---|---|---|
| D1 | **只对共享卷启用 ledger** | 本地卷落盘零收益 | 卷类型判定错误 ⇒ 静默失效 ⇒ 必须有**门禁/指标**兜住（见 §6 V3） |
| D2 | **append-only 分片 + 无锁** | 共享卷上跨进程锁不可靠 | 读需扫全部 shard ⇒ **压缩**控制成本（S3）；shard 数量随进程数增长 ⇒ 需回收 |
| D3 | **对账为最终权威** | 已有机制、可自愈 | 崩溃窗口内**可能少计**（多写）⇒ 方向是「可能超限」而非「误拒」；由对账周期约束窗口 |
| D4 | **账本不可读 ⇒ 跳过 + 计数**，不 fail-open | 限额被静默放宽是最危险形态 | 需要告警面消费（复用 `alerts`/metrics） |
| D5 | **不改 `pkg/quota`** | 保持通用领域模型纯净（G0 分层） | ledger 逻辑落在 capacity 层 ⇒ 该包职责变重（可接受，已有同类范式） |
| D6 | **不新增配置开关** | 避免「忘配 ⇒ 静默降级」 | 无法为特殊卷**关闭** ledger（如已知不共享的 s3 卷）⇒ 可留**显式** opt-out（需裁定，见 §8 Q2） |

## §7 风险与不变量

- **R1 超限窗口**：崩溃未 flush + 对账周期之间**可能少计** ⇒ 方向为「可能超限」（不是误拒）。
  缓解：对账周期（既有配置）+ 写入前 `TryAdd` 的**卷级**硬上限（已持久化 ✓）仍生效 ⇒ **卷打满**仍被拦。
- **R2 shard 膨胀**：进程频繁重启 ⇒ 分片多。缓解：S3 压缩 + epoch 回收。
- **R3 分布式语义边界**：本设计**不**提供线性一致性（不做锁）；只保证「最终不超限（对账后）」+
  「在途期间按可见分片求和」。**这是刻意的**（P2），必须在文档与配置说明中写明。
- **R4 卷类型判定错误** ⇒ ledger 静默不启用。缓解：V3 + 指标 + 装配期显式日志（本项目既定「生效状态必须可观测」）。

## §9 与既有设计的衔接

- 本设计**不**改变配额模型 v3 的记账口径（只按物理占用 ✓、每卷独立 ✓、用户每卷独立 ✓、目录级上限 ✓）；
- 本设计**不**触碰 `§13`（写侧统一）——该片已按 §13.1b **撤回**（结构性偏好，非缺陷修复）；
- 本设计**沿用**「释放 ≠ 结算」类的**单一收口**纪律（本会话已把该类收敛为 `releaseChargeFor` 单点）：
  ledger 的 `Commit/Release` 必须与该收口**同源**，不得各自解释尺寸口径。
