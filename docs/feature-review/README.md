# 功能对抗审查（Feature Adversarial Review）

> 对 roadmap「已落地」全部功能做对抗审查，覆盖四个维度：**正确性 / 可用性 / 安全性 / 可维护性**。
> 每批并发多路 reviewer，审查结果落盘本文档目录，作为功能健康档案与后续改进输入。

## 审查维度

| 维度 | 关注点 |
|------|--------|
| **正确性** | 功能行为是否符合规格；边界条件；竞态；数据一致性 |
| **可用性** | 用户可操作性；错误信息；恢复路径；幂等性 |
| **安全性** | 认证/授权；路径穿越；注入；密钥管理；fail-closed |
| **可维护性** | 代码结构；可测试性；文档同步；技术债 |

## 发现分级

| 级别 | 定义 | 处置 |
|------|------|------|
| **P0 严重** | 数据丢失/安全漏洞/可复现崩溃 | 立即修复 |
| **P1 重要** | 功能缺陷/边界错误/性能隐患 | 排期修复 |
| **P2 一般** | 可用性/可维护性改进 | 记录 |
| **P3 建议** | 风格/文档/小改进 | 参考 |

## 批次划分

| 批次 | 范围 | 审查文件 |

## 审查记录模板

每功能审查结果按以下模板落盘（`NN-<功能名>.md`）：

```markdown
# 审查：<功能名>

- **批次**：N
- **审查者**：<reviewer id>
- **审查日期**：YYYY-MM-DD
- **审查基线**：<commit hash>
- **维度覆盖**：正确性/可用性/安全性/可维护性

## 结论

**总评**：通过 / 有条件通过 / 未通过
**发现数**：P0 x / P1 x / P2 x / P3 x
```

## 批次执行

- 每批 2-3 路并发（按批次表）
- 每路审查独立 worktree 只读基线，互不依赖
- 每批完成 → 更新 `review-status.md` → 开始下一批
- **全部批次完成后**：汇总结论 + 发现清单到 `summary.md`，提交 docs-only PR
