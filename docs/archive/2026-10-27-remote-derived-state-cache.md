# 远端派生状态缓存与删除失效纪律 — 归档

> 现行事实源见 `docs/architecture.md`「远端派生状态缓存与删除失效纪律」（分类表 / 产出契约 /
> 消费三段式 / 删除三段式）与门禁 **R39**（`delete_invalidation_gate_test.go`，`docs/gates.md`）。
> 本文件只保留**分类判据 / 四层机制的设计意图与取舍 / 仍有效的判断 / 未决项 / 落地指针**；
> 分期清单与验收（已进权威文档或已实现）已移除。

## 背景
仓库里有一批「从远端卷内容 / 对象内容派生出来的本地状态」。它们让操作变快，但底层事实变化后
本地副本会撒谎。原文的起点是 2026-10-27「外部卷删除/改名报缺少 checksum」的根因复盘：
顺着它追下去暴露的是**仓库缺少统一的「远端派生状态」分类与失效纪律**（各卷各写一套：
secretdata 有 `invalidatePrefix`、baidupcs 的 dlink 删除时**完全不清**、搜索索引/checksum 台账
只有本地卷生效）。

## 分类（按「陈旧会造成什么后果」定失效强度，最核心的结论）
| 类别 | 定义 | 陈旧后果 | 允许的过期强度 |
|---|---|---|---|
| **A 内容派生值** | checksum / size / mtime / 明文块 | **安全**：错误「一致」会放过被篡改文件；错误「不一致」会误拒合法操作 | **强一致或 fail-closed**，禁止乐观复用 |
| **B 句柄/凭据** | dlink URL、access token | 可用性失败，可观测、可自愈（重新签发） | TTL + 失败自愈 |
| **C 结构视图** | 目录树 / 文件索引 / 聚合列表 | 幽灵条目、看不到新文件 | 中（必须有明确收敛路径，不可永久漂移） |
| **D 聚合账本** | 配额用量、容量计数 | 假 507 / 过度准入 | 强，但允许有界漂移 + 对账 |

判定口诀：*能导致「把坏数据当好数据」的是 A 类，必须强一致；只影响「这次失败下次再试」的是
B 类，TTL 就够。*

## 四层机制（设计意图，仍有效）
1. **产出契约**——`sync.Entry.Checksum` 允许为空（= 未知，调用方按需 stat）；但底层能**零额外
   I/O** 给出整文件 SHA-256（内存态）的卷**必须填**（secretdata 的 `Original.SHA256`，O(1)）。
   远端逐文件一次 RTT 的卷保持 unknown 由消费方 stat 兜底。`ChecksumType` **必须自述算法**
   （baidupcs 的 `etag` 不是整文件 SHA-256）。**最终实现与本条的偏差**：原文举例「S3 填 ETag」
   被否决——`baidupcs`/`S3` 的 etag **不得**被当作 SHA-256 比较（架构文档已收敛为此口径）。
2. **消费侧三段式**（任何需要 checksum 才安全的写操作）：① 调用方给了 → 用；② 没给 → Stat /
   FileMeta 现取（A 类禁止用缓存猜）；③ 仍拿不到 → **明确拒绝**（fail-closed）。前端
   `resolveOpChecksum`、CLI `FileClient.resolveDeleteChecksum` 即此形状。
3. **失效总线**——不再造大而全缓存层，统一「对象身份 + 失效信号」的传达方式：任何 FS 实现
   在 `Delete` / `Rename` / `WriteFile` 成功后必须让自己的派生状态对相应 `ObjectRef` 不再生效。
   三种可接受实现：① 即时清除（键空间有限、可精确映射）；② 代际递增（结构化视图）；
   ③ 短 TTL（B 类句柄）。
4. **删除三段式**（**顺序不可颠倒**）：① 删前校验（口径是「防误删」而非「防篡改」——用 sidecar
   记录值比对，不重算）；② 删远端失败 ⇒ 本地**一律不动**（不释放配额、不清缓存），保持可重试；
   ③ 确认成功后才失效本地派生状态（内容/结构/句柄即时清、账本用删前实测字节释放、审计发布）——
   **任一项失败只 Warn + 记指标，绝不回滚 ②**。

## 仍有效的判断（最重要）
- *凡是**本进程之外**可能被删除的东西（外部卷、多实例共享卷、用户直接用网盘 App 改的卷），
  其派生值要么不缓存、要么有 TTL/重扫——不能靠「我删的时候记得清」。* A 类不缓存（每次现取）；
  B 类 TTL + 自愈；C 类需重扫；D 类靠对账。
- **删除后不失效**才是真正危险（幽灵存在到 TTL）；「先删远端再清缓存」的中间窗口读到旧缓存但对象
  已不存在，下次 404 可接受，故顺序是三段式。

## 落地指针
- 门禁 **R39**（`internal/archcheck/delete_invalidation_gate_test.go`）：持派生缓存的卷实现，
  其删除/移动路径必须失效该缓存。
- `pkg/volume/ext/baidupcs` 的 `invalidateDlink`（删除/移动后主动失效直链缓存，`storage.go`）；
  `pkg/volume/secretdata` 的 `ListDir` 填 `Entry.Checksum`；`pkg/sync` 的消费三段式。

## 未决项（原文 §6，S5）
**外部/多实例改动的感知**（secretdata 索引只在挂载时扫一次）原文给三选项并**需产品裁定**：
- A：不支持，文档明确声明「卷根目录不得被 sproxy 之外的进程修改」（成本 0，风险是幽灵条目不收敛）；
- B：加显式刷新入口（重新 `loadIndex`，需处理并发写）；
- C：后台定期探测（容器数/mtime 抽样，网盘上探测本身要 RTT）。
⇒ 后续演进见 `docs/archive/2026-10-28-volume-state-maintenance.md` 的
显式刷新契约（默认永不过期 + `sclient volume refresh`），沿 B 方向落地。
