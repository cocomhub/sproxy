# 架构决策与协议选择（2026-08 评估）

> 来源：`docs/superpowers/learnings/2026-08-04-*` 三份架构分析（架构全景 / 过度设计 / 开源对比）。
> 历史价值：记录了隧道分层架构的**设计动机与取舍标准**、过度设计的识别方法、以及开源生态定位。
> 注意：当时的「过度设计」结论（QUIC/gRPC/WebRTC/DHT/P2P 无消费）已被后续组网演进推翻——
> 2026-08-30 起的 mesh 阶段把 webrtc/DHT/P2P 全部接入了真实产品场景。**判断「过度设计」要结合当下路线图，不是一次性的。** 本文只保留仍有效的方法论与协议取舍标准。

## 1. 分层架构的动机（tunnel_mux 的核心价值）

```
传统隧道（POST /tunnel）：单向请求-响应——客户端主动发起，服务端被动响应
多路复用隧道（tunnel_mux + mux）：双向——两端均可主动发起请求
```

- **双向通信能力是 tunnel_mux/mux 存在的根本理由**（中继转发场景必须），不是性能或加密
- 消费链（2026-08-04 实测）：`pkg/client WithXfer("ws")`、`cmd/sclient relay`、`pkg/server relayHandler` 三个真实消费者
- 传输层抽象（xfer.Conn: Send/Receive/Close）成本低、接口清晰，保留；具体扩展按场景取舍

## 2. 协议选择的判断标准（仍然有效）

> **协议的价值 = 它解决的问题是否在你的场景中存在。**

| 传输协议 | 适用场景 | 取舍建议 |
|----------|----------|----------|
| TCP/HTTP | 公网/内网直连、低延迟高吞吐 | 核心，0 额外依赖 |
| WebSocket | 防火墙友好、NAT 穿透、浏览器 | 中继/穿透场景核心；WSS 可配合 CDN |
| QUIC | UDP 环境、弱网优化、0-RTT | 有明确场景再引入（移动端等），维护成本高 |
| gRPC | 多语言微服务双向流 | 无多语言需求则不引入（HTTP/2 指纹明显） |
| WebRTC | P2P 直连 NAT 穿透（无需中继） | 打洞场景有价值（后续 mesh 已实际采用） |

维护成本权衡：每多一种传输 = 独立 go.mod + 构建/测试/文档/版本升级维护。
**默认固定 TCP + WS，其它按真实需求引入。**

## 3. 过度设计识别方法（方法论仍有效）

1. **消费链追踪**：先确认「产品代码有没有消费端」再判过度——不能凭印象（2026-08-04 初判 tunnel_mux 0 消费是错的，实际 3 个消费者）
2. **按层量化**：逐层统计文件行数 + 消费端 + 状态（✅核心 / ⚠️有消费可精简 / 🔴无消费）
3. **区分「技术成立」与「场景需要」**：QUIC/gRPC 技术上没问题，但当时 0 场景
4. **安全深度的边际收益**：AES-256-GCM 认证加密已足够时，ECDH PFS + 重放保护属过度（但后续需求变化可重新评估）
5. **「分离关注点」过度延伸**：xfer → mux → tunnel 三层替换设计对通用中间件库合理，对具体应用需验证每层都有消费者

**重要修正**：过度设计判断是**时间点快照**。2026-08-30 起 mesh 组网阶段将 webrtc/DHT/P2P 全部接线为真实功能，
证明「当前无消费」不等于「永远无消费」——评估时结合路线图，识别时保留可复用件（接口抽象、模块边界）而非整体否定。

## 4. 跨墙 / 跨网络场景（协议选择由流量特征可识别性决定）

- 跨墙场景关键不是「加密强不强」，而是「流量看起来像不像正常网络流量」（DPI + 主动探测）
- **CDN 前置比协议选择更重要**：SNI 显示 CDN 域名，极难针对性封锁
- WS over TLS（WSS）+ CDN 是伪装度/维护成本平衡最佳（大量 Web 应用使用 WS，流量混杂）
- 纯 TCP 自定义帧隧道 DPI 特征明显；gRPC 的 HTTP/2 SETTINGS 帧 + Content-Type 是强指纹
- 不做自实现协议混淆层（GFW 跟进封锁快于你迭代）
- 链路选择优先级：直连 → 隧道(TCP) → 中继(WS) 三级 fallback 有价值；请求级动态路由（大文件直连小请求隧道）复杂度过高收益不清

## 5. 开源定位（2026-08-04 评估，格局类结论仍具参考性）

- sproxy = 「文件服务 + 加密隧道 + 中继网络」三合一，单二进制零外部依赖
- 独特差异：Go SDK、Checksum 全链路强制、隧道与文件 API 深度融合、NAT 穿透
- 不适合与其正面对抗的领域：企业级文件管理平台（Cloudreve/Filestash）、高性能反向代理（frp）、公网文件分享（PsiTransfer）
- 建议定位：面向开发者和自动化场景的安全文件传输基础设施
- 当时列出的短板（多存储后端、WebDAV、用户管理）已在 2026-09 通过 volume 框架 + WebDAV 网关 + 凭据 store 补齐——**短板清单是路线图输入而非永久缺陷**
